# P7 S2 多 worker 与静态处理组设计

日期：2026-11-11。当前状态：**S2a已在 `p7-s2a-exit=f720ef571df72682d56732876f03c79f076eca45` 退出；S2b已确认业务边界和热新增要求，详细设计/计划已通过Astra独审与复审、具备代码实施条件，产品未实施。** S2a结果见[总结](p7-s2a-summary.md)；S2b当前入口为[详细设计](p7-s2b-design.md)、[执行计划](p7-s2b-execution-plan.md)和[S0 §15](p7-s0-owner-decisions.md#15-s2b-业务收口与设计审核授权2026-11-11)。下文S2a算法及早期准备记录按历史时点阅读，不以旧“未实施”文字覆盖exit。

依据：[S0 本轮决议 §12](p7-s0-owner-decisions.md#12-s2-简单性与业务边界收口2026-11-11)、[总体设计](p7-design.md)、[执行计划](p7-execution-plan.md)、[处理组与设备副本](p7-processing-groups-and-test-extraction-design.md)。本稿收窄早期 S2 的可选能力；现行 owning Contract 在实现前按实际变更修订，不将目标描述冒称已经生效。

## 1. 目标与简单性约束

日常业务是上传、预览、人工确认、提交；实际计算可持续数十秒至分钟，同组单 worker 易使不同用户互相等待。保留组内多 worker，接受极端并发时排队，不承诺零等待或线性吞吐。排队提示及前后端交互另行设计；资源上限、原期限与未完成输入保护仍是执行机制责任。

新增机制必须对应当前业务能力及具体失败后果。优先复用现有事务/CAS、租约、幂等、checkpoint、标准进程管理和文件原子发布；复杂度过高时重开业务范围，不自动追加调度服务、协调数据库、跨进程缓存生成协议或通用恢复状态机。不可逆业务事实的正确性不能通过缩小验证代替。

## 2. 阶段划分与实施顺序

**建议并沿用现有顺序：S2a 先完成，S2b 后完成；共用本设计，不合并为一个产品退出阶段。** Owner 本轮询问合并可行性，尚未另行确认改变阶段顺序，本节不把建议登记为新的 Owner 决议。

| 阶段 | 最小交付 | 独立证明的边界 |
| --- | --- | --- |
| S2a | 单组、单 backend 服务实例、单 RS 服务实例，固定多个 worker | 共享 DB/roots 下领取、执行、恢复、缓存和资源正确 |
| S2b | 同机至少两个独立完整组，静态设备归属和路由、分别选择版本组合/资源配置 | 不共享可写业务状态，错误路由被拒绝，一组维护不停止另一组 |

灰度自动化后移减少了 S2b 的功能量，但没有消除组路由、独立部署、目录与数据隔离风险。两类问题合在一次实现/取证中会扩大定位范围，也使本可独立使用的 S2a 等待分组接线。S2b 设计和配置接口可提前准备，产品实施依次推进；无需人为插入长等待或重复设计会话。

各阶段内部只做必要 focused 和边界验证，在阶段最终候选集中完成实际受影响包/容器及已确认真实范围。S2b 复用 S2a 测试 owner，证据沿用由现有闭包/容器规则判定；闭包变化必须重跑，不能以“复用”免验。保持独立阶段退出，不将内部工作包变成额外全量门禁。若未来确需合并退出，另明确调整计划与证据范围，不由实现者静默合并。

## 3. 业务并发与同库提交

多人可以在各自 Workspace 上传和预览，产出基于同一 baseline 的兄弟 Submission。人工查看期间不占 worker，不把用户会话绑定到某个 worker；同一 operation 的后续步骤可由另一 worker 领取。独立预览与 History compare 按冻结输入和实际资源边界判断并发，不新增覆盖设备整个业务流程的大锁。

来源解释按实际 initial/modified 完整身份和现有归档规则，不以提交早晚推断源数据顺序。候选可形成多种对应关系；缺少来源证据时保留诊断，候选补齐后可以重新核验，不能仅凭时间自动消除异常。并列候选不会自动合并修改；归档仍选择已有完整状态，真实 baseline 漂移仍受 Preview/Submit/Review 既有版本门禁约束。

同 repository 写入继续使用现有 SubmitAttempt 占用：

- T1 受理取得 repository/Workspace 占用并冻结 expected technical commit；同库已有未完成 Attempt 时，第二个 Submit 沿现有占用冲突拒绝，不另建“已受理待提交”队列。
- finalize 后释放 repository 占用；Submission 可以继续待审核，仅保留其 Workspace 占用。其他 Workspace 此后可以提交，业务上形成同 baseline 的兄弟节点。
- 写入结果 UNKNOWN、失租或普通 Operation terminal status 不能单独释放占用。先查询原请求，确认发布后 finalize，或证明未发布且原请求不再继续后终止。
- PENDING 的退回/撤回、APPROVED 的有理由关闭不归档沿现有权限和版本规则；没有通用“管理员清锁后继续写”的出口。

已受理任务排队与尚未满足受理条件的请求分别表达。后续 UI 不能把占用冲突伪装成已受理排队；自动受理同库多个 Submit 会改变冻结时点和恢复语义，须重开本边界。

## 4. 领取与共享资源

复用持久 operation/step 队列及其可执行时间、创建时间、稳定 ID 顺序，通过短 DB 事务原子领取。S2a 不引入新队列、交互优先、设备公平或抢占；这些留 S3。领取、心跳、checkpoint 和结果发布继续使用 lease token/CAS，不在 DB 写事务内执行计算、文件哈希或 RS 网络等待。

History compare 是不改变业务历史的计算操作，不是物理无写入：它会写派生产物、缓存索引、任务状态和保护记录，缓存命中也可能更新保护/TTL。Upload 已可与 worker 并发；增加 worker 后必须验证所有共享消费者，不能仅审 Dolt 写锁。

| 资源 | 现有基础与 S2a 约束 |
| --- | --- |
| artifact 文件 | 独立 staging、完整校验、原子 no-replace 发布；目标已存在时验证，不能原地覆盖半成品 |
| 缓存索引/保护 | SQLite 短事务；完整值才发布索引，失效删除核对原记录，不误删另一执行者的新值 |
| 正常读写与 cleanup | root 共享借用与持久保护；cleanup 非阻塞尝试独占。核锁顺序与 root 粒度，不把现有保护误当“全部业务串行” |
| exact-commit 派生对象修复 | 从指定 commit 重建；替换损坏对象按现有独占保护和 busy 语义，不切到可变 main 补数据 |
| RS 写入/读取 | 同库 writer 边界保持；缓存缺失后的 exact-commit 导出与 import 真实互斥范围须源码复核和集成验证，不预称读写无等待 |

允许同缓存 key 同时 miss 后重复计算，重复量受固定 worker 和资源上限约束；不为消除重复计算增加跨进程 single-flight 租约/等待队列。所有表存储、导出缓存和计算缓存路径分别核实保护闭包；发现正确性缺口先修复，不能把上表当成已通过多 worker 验证。

## 5. 固定规模和资源预算

首版每组固定 `W=K`，每 worker 最多一个 executor；这里 K 为组内执行上限，单组时也是该组对整机的执行贡献，多组整机预算累计各组。不存在独立全局槽位分配器。替代旧的可选 `W>K` 方案；不做自动扩缩容、资源超配、任务大小预测或大小任务分池。

同组 worker 使用相同 CPU/内存/kernel 配置。按所有 W 个 worker 同时执行规划 `W×E`、backend/RS/Dolt、OS 与共享余量；M 是 kernel 准入预算，不是 RSS。CPU 同时计 kernel、Arrow、RS 等实际消耗。S1b 统计用于观测与人工调参，不成为任务归属、成功或实时容量的权威。

默认保留 N=1，先验证最小两个 worker，不同时放开单任务内部并行。两个 worker 是验证目标，不是已确认生产默认值，更不意味着任意现有节点都能承载：例如两个 32 GiB envelope 已占满 64 GiB，尚未计共享服务，不能直接如此运行。实际节点/配置须符合预算和既有授权；不擅自降低安全余量或改变产品默认来凑并发。

配置变更通过维护停止/重启生效。固定 W 依靠受控部署的实际进程数，不只看 JSON；启动替代实例前须确认旧实例及执行子进程已退出，不以租约过期证明 CPU/内存已释放。

## 6. 故障与维护

Owner 接受暂时降容、个别任务等待及人工恢复，不承诺无感接管或几秒内恢复。普通任务失败不扩成组故障；新 worker 看到其他有效租约应承认其正常执行，不能误接管或因此全局拒启。失效任务沿原能力分类、有限预算、幂等和 CAS 恢复；固定实例各自恢复自己的遗留RUNNING，其他实例不抢占；同固定编号重复启动竞争须只有一个取得生命周期锁。固定worker_id与随机lease_token分别表达实例归属和领取代际，细节见[S2a计划§3–§4](p7-s2a-execution-plan.md#3-固定实例身份和进程边界)。

纯计算可按原 checkpoint 重算；外部 effect 先核原结果，不换请求 key 盲重放。旧执行者失租后不能发布有效业务结果。无权威停止证据或无法确定写入结果时保留必要阻塞并交人工处理；不建设 worker 互相杀进程、自动故障迁移或无限恢复服务。重启使用现有标准进程管理；启动/扫描接点已具体化于S2a计划；不引入peer周期接管。

故障范围按事实确定：可归属任务/repository 的问题限制在相应范围；共享 DB 损坏、root 身份异常等组级问题不可绕过。组级保护不得被“其他 worker 继续”要求放宽。

正常维护流程为：暂停本组新重任务受理、停止新 claim → 当前工作正常完成或按已有协作交接规则停止 → 确认旧进程退出 → 修改配置/版本 → 启动核验和恢复后继续领取。具体使用进程内AdmissionGate、内部drain接口和一次性运维脚本，不设新持久维护状态机。worker停止后RS/backend仍可写，root/身份/版本变更前须再停止backend、RS及Dolt子进程并核原UNKNOWN结果；详细顺序见[S2a计划§7](p7-s2a-execution-plan.md#7-维护入口闭门停止领取保留队列)。

“排空”不要求执行完整个待执行队列。QUEUED 等已受理任务留在持久队列，维护不等于用户取消。保留原有绝对期限、恢复预算、输入和 checkpoint 保护；不冻结停机期间计时，不在重启时自动延长期限、清占用或重置次数。现有 drain 上限和无自动强杀业务事务约束保持，无法安全完成时明确阻塞。状态查询及必要人工处置保留。组内升级使用维护窗口，不支持组内滚动混跑；S2b 的组间不同版本独立运行是另一边界。

## 7. S2b：静态组与未来灰度

处理组的已确认用途是后续按设备分批升级、限制新版本影响面，同时可独立配置资源。每组是完整部署单元：一个 backend 服务实例、一个 RS 服务实例、worker 池、独立 control DB/RS 状态/Dolt 与全部可写 roots。组内使用一套明确且经过验证的版本组合，不必强制未变化组件升级，但不承诺任意版本混搭。凭据/端点/挂载不能误连另一组。

S2b 最小交付为静态设备归属、组路由与接收组检查、独立端口/卷/配置/生命周期/资源预算，以及组/环境/版本可识别的日志和统计。普通业务状态仍归组内；归属目录只保存必要归属，不扩成全局队列、租约或审核数据库。目录采用受控文件，不预建目录服务或在线换组协议。设备每个正式环境只有一个有效写入组；新增设备必须热更新、不暂停已有设备和在途任务；程序/资源/root变更仅相关组维护。在线注册、入口平滑更新和失败处理按[S2b详细设计](p7-s2b-design.md)，此处替代早期全部配置维护更新的限制。

首版建议预设小型固定设备组，以后先升级该组，再逐组升级，不为每次发布搬迁设备。S2b 不交付自动分流、自动判定灰度通过、自动回退、在线迁移或跨组均衡。可先验证两个同版本独立组及各组版本配置独立性；真实跨版本灰度能力未验证前不得宣称可用，不为阶段门禁制造兼容版本。

未来发布先用相同起点/输入的隔离副本比较，再小组正式灰度；业务规则有意变化时解释预期差异。不能以不同设备负载直接证明新旧版本等价。正式灰度不允许新旧组同时推进同一设备业务历史。共享宿主/磁盘故障仍可影响多组，服务隔离不冒称硬件完全隔离。

独立部署不等于无损回退。新版写过 schema/持久格式或业务事实后，旧镜像未必可读；恢复升级前副本也可能丢失新增正式操作。实际灰度启用前按版本明确 API/客户端适配、迁移、数据备份/恢复和新增操作处置。当前继续单一基线 schema、无兼容层；首次需要保留部署数据时再引入前向 migration，不预建任意版本降级平台。

## 8. S4b：设备全状态抽取与加载

保留[分组副本设计 §4–§9](p7-processing-groups-and-test-extraction-design.md#4-默认抽取内容)的完整设备副本能力：默认全部现存历史/审核/Workspace/终态及未完成任务、RS 状态、必要文件与关联依赖；不只复制 Dolt 表，不人工勾选部分历史。

首版允许源组维护窗口：停止所有相关 writer、cleanup 和维护后捕获一致集合，不要求先把 pending 跑完；其他设备暂受同组停机影响。副本使用独立环境身份、凭据、端点与可写数据，保留原 ID 和故障事实，缺失/未知不补造成功，原版本/schema 不兼容明确拒绝。原包不可修改，实验在可写副本进行；单向复制，无回合并。

S2 现在只守住 group/environment、数据 owner、明确可枚举持久记录和引用边界，不把唯一恢复事实藏在内存或跨组共享可写状态，不预建通用依赖图。导出表清单、闭包枚举和加载工具由 S4b 实现。生产换组是排空后的唯一写入责任转交，不是测试复制；工具/流程仍在 S4b，S2b 不提前承担搬迁能力。

## 9. 最小验证责任

| 阶段/owner | 必须验证的行为 |
| --- | --- |
| S2a Operations | 至少两个 worker 共存与竞争领取；有效租约不误恢复；迟到结果拒绝；同固定实例启动竞争/原实例恢复、有限重试和人工状态；健康任务不错误接管 |
| S2a Submission/RS | 同库 Submit 占用冲突、finalize 后新提交、UNKNOWN 先查结果且不重复写入；独立设备仍可运行 |
| S2a Artifact/cache | 同 key miss 并发发布、读取与清理交错、发布中断、失效删除不伤新值；缺缓存的 exact-commit 读取与 import 交错 |
| S2a 部署 | 实际 W/CPU/内存限制；停新受理/claim、协作退出、待执行队列重启；不多启动旧实例残留；原期限/保护不被重置 |
| S2b 路由/部署 | 两组独立 DB/卷/RS/端点，错误归属拒绝，维护一组不停止另一组；资源累计、共享磁盘不重复承诺；组版本配置独立 |
| S4b 抽取 owner | 一致捕获、完整依赖、未完成/未知结果、源副本隔离、缺损/超容量/版本拒绝，沿原设计验证 |

复用 owning 测试，每个不变量一个权威 owner，不穷举内部锁调度，不建设重复全故障矩阵。专用节点、clean 已提交源码、离线缓存及阶段门禁遵守仓库规则；真实输入范围仍依 DC33 在实施准备时确认，本轮文档授权不自动扩展真实数据范围。

S1b 移交的 D24：N>1 开放前同真实输入 N2/N1 正式结果/digest 一致核对，最迟 S5；合格 t4 D23 参考仍最迟 S5 闭合。多 worker 并发不替代 kernel N2 核对，保留 N1 不等于取消后续责任。

## 10. 实施准备仍需具体化的工程事项

业务边界已足够。下列S2a工程事项已核源码并纳入[详细实施计划](p7-s2a-execution-plan.md)，本轮已独审闭合；产品能力仍未实施。S2b条目留其实施准备，不阻塞S2a：

1. 核 `operations/worker_startup.py`、`recovery.py`、`persistence.py` 与 `sqlite_operations.py`：活动记录扫描的并发视图、有效/过期租约分类、恢复领取 CAS、任务局部阻塞及现有故障分类；确定最小改动和状态迁移。
2. 核 `worker_runtime.py`、部署入口与现有进程管理：实际 W 约束、退出确认、启动次序、维护接线和观测；不得把进程内计数当跨进程权威。
3. 核 `submission/accept*.py`、`finalize_transaction.py`、RS admission/locks 与 exact-commit export：现有占用何时获取释放、资源等待上限、读写互斥和恢复接点。
4. 逐项核 `artifact_store`、computation/export/canonical cache 的事务、锁顺序与保护存活期；仅修复具体缺口，不复制协调机制。
