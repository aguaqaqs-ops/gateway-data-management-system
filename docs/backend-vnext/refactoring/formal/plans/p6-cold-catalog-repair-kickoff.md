# Phase 6 冷 catalog 最小修复候选

状态：2026-11-06，设计候选，待独立范围审核；本文不放行产品修改、节点测试或正式测量恢复。授权背景为 DC80 的主动诊断与最小修复；诊断依据见 [单步诊断审核 §20–21](p6-submit-single-step-diagnostic-scope-review.md)。不修改已交新开发设计会话维护的 DC81、执行计划与 S2b kickoff。

## 1. 已知问题与目标

冻结产品 `e798ec87a37330250b0c051162e7962dba1daa60` 的独立副本冷 catalog 调用最终 ReadTimeout。三份有效 RS 栈显示请求等待逐表 schema/COUNT，且后续重试与先前同 key 加载重叠。该证据没有证明某个 Dolt 子命令的完整耗时，也没有解释原 Submit 的 `lease_lost`。不重复相同诊断，不重开完整 Submit 来代替局部验证。

本候选分别处理两件事：减少精确 COUNT 的 CLI 启动次数；合并同一 `(repository_id, commit_id)` 的进行中加载。首次冷读是否能在原客户端预算内完成是待验证结果，不因进程数减少就宣布修复。H3 已通过，保留原证据；W4/S4/H1 与剩余正式测量仍停止。

## 2. 产品范围与预算裁定

从冻结 e798 建立独立修复候选，不在冻结 worktree 原地改写，也不把 main 的其他产品变化带入。拟修改范围仅为：

- `candidate_a/dolt_cli.py` 的 `catalog_at` 精确 COUNT 获取及私有辅助函数；schema 仍使用原逐表 `_load_table_schema`，不改变 import `catalog`、`type_catalog` 或其他查询路径。
- `versioned_read/application.py` 的现有进程内 catalog cache，加入同 key 的进行中加载合并。
- 对应 focused 测试与独立 handoff。不改 Contract DTO、依赖、Dolt 版本、Dockerfile、持久格式、HTTP timeout/retry、全局 capture 或通用进程执行器。

COUNT 每批最多 **16 张表**，生成一条 `UNION ALL` 查询、返回一个 JSON 结果。每项包含由程序生成的 ordinal 和精确 `COUNT(*)`，全部表都使用同一冻结 commit 的 `AS OF`；标识符和 commit 使用现有转义函数。不依赖结果自然顺序，严格校验 ordinal 的类型、范围、完整性、唯一性及其表映射；count 沿用既有非负精确整数解析。没有表时不发 COUNT。任何查询失败、截断或形状不符均拒绝整个 catalog，不发布部分缓存。

**明确接受的候选预算变化：每个批量 COUNT 查询共用现有 metadata 命令预算（冻结配置为 30 秒），而非每张表分别获得 30 秒。** 这是内部工作预算收紧，可能使原先逐表可完成但一批总耗时超过预算的输入更早失败；不声称完全行为等价。失败保持原 provider 错误类别，不返回估计 count、部分成功、旧缓存或自动退回逐表重试。若范围审核发现 owning Contract 承诺逐表成功时限，先回设计，不能直接实施。本项目没有兼容要求，但精确结果与资源边界不因此放宽。

保持原单命令 **256 KiB** 输出上限；此处只合并最多 16 行 ordinal/count，不合并 DDL，不新增多 JSON framing 或 per-call capture 接线。使用原并发配置的上限，冻结配置为两路；不新增嵌套池或同时执行两套独立池。每批与 schema 调度需在实施 handoff 说明，任务枚举有界；最终表排序、schema、row_count、视图排除和 DTO 语义不变。并行执行下内部失败发现顺序不作为新的外部承诺。

不选择“16×30=480 秒”批命令：它会放宽单查询存活时间，并可能扩大请求超时后的后台工作。不引入按输出进度重置 deadline 的新协议：现有执行器没有逐 SQL 结果计时能力，观察到结果不等于 SQL 起止，不能把该协议称为保留原计时语义。

## 3. 同 key 加载合并

使用标准 Future 和现有锁；一个 leader 在原请求线程运行 loader，followers 在锁外等待同一结果，不新增 executor。缓存命中与 leader 选取必须原子协调；不同 key 不因持锁运行 loader 而串行。

成功仍按现有 8 项/16 MiB LRU 限额缓存；超过缓存预算的结果只共享给本次等待者，不留存。失败不缓存，所有 leader 退出路径都完成 Future 并移除对应 in-flight 项，后续新请求可再加载。不得因 leader 的异常或取消留下永久 pending Future；异常继续由原 provider/HTTP 边界映射，不新增公共错误码。

本候选不新增关闭状态机、持久任务、负缓存、后台线程或跨进程协调。沿用现有同步请求和 Dolt 有界进程生命周期；不把 Future.cancel 解释为停止 Dolt，也不宣称客户端断连会取消 leader。关闭行为若需要额外产品接线才能避免本次新增的 waiter 悬挂，先提交具体缺口回设计，只补必要边界。已有服务关闭的整体问题不在本候选中静默扩项。

## 4. 最小验证与停止

范围审核通过后再下达实施与节点验证任务。调试仅在 05 的 clean 已提交候选进行，先核 SSH、离线缓存和有效占用；不抢前端或新开发线的节点窗口。开发主机不运行测试。验证集中为：

1. 复用已有解析不变量，补批边界、ordinal 错形状/缺失/重复与整批失败不缓存；不复制全类型矩阵，不为纯解析建 Dolt fixture。
2. 一个小真实 Dolt 场景对同一冻结 commit 比较新查询与原精确结果，包含跨批边界和必要的标识符转义；证明 schema、count、排序相等。对历史 commit 的读取不能混入当前 main。
3. 用事件同步验证同 key 一次 loader、不同 key 可并发、失败后可重试、超缓存预算仅本次共享及 leader 异常释放等待者。时序测试标记 serial，不用随意 sleep 或新外部进程矩阵。
4. 代码与 focused 通过独立审核后，另准备新 RS 镜像候选，仅在既有已核 75 MB 源 RS 卷的独立副本做一次冷 catalog 调用。沿用原客户端 30 秒及最多三次内部尝试，不预热。只有新 RS 进程的 **attempt 1** 成功，才支持首次冷读改善；attempt 2/3 或暖缓存成功不替代。记录完整 catalog 身份，精确对照方案须先审，不重复扫描所有历史卷。

第四步须有具体产品提交、镜像身份、单次预算、执行脚本和独立 GO；本文不是其启动凭据。若仍失败，保留结果并回到局部设计，不自动重跑或调 timeout。即使成功，也不证明原 lease 问题解决。最终产品门禁按实际变更包和容器边界办理，不能用 focused 或本次诊断代替；不在调试期间先跑全量 runner。
