# 未来扩展方向：自然语言业务数据查询

- 状态：**方向记录（Exploratory Direction）**，待单独详细讨论。本文不是 Contract 或 ADR，不改变任何现行阶段的范围，不授权实现。
- 日期：2026-09-27
- Owner：Backend vNext Architecture
- 适用时机：语义模型的记录可以随时开始；服务端实现在 P5 整体 exit 之后
- 事实基线：`main` @ `43b59ca3c1`
- 索引：[架构总纲 §16](architecture-and-refactoring-plan.md#16-未来扩展方向)；相关方向：[分析能力工具化与 AI 编排](future-ai-tool-exposure.md)

## 1. 目标

增加 MCP 接口用于查找当前业务数据。owner 将记录业务数据表之间的关系与查找逻辑；使用者以自然语言向 agent 提问，agent 依据
已记录的关系与逻辑查找数据并返回结果。

## 2. 方向结论

1. 模型负责理解意图，查询由确定性引擎执行。模型从已登记的查找逻辑中选择、把名称解析为键、填写参数并解释结果；
   执行计划由语义模型编译，在指定 commit 的只读数据上执行。
2. 不采用由模型直接生成 SQL 的方案（text-to-SQL）作为主路径，原因：
   - 配置表之间的关系多为业务约定，不是数据库外键，模型容易连错；
   - 已记录的关系与查找逻辑可能被绕过；
   - 同一问题的生成结果不稳定，无法复现与审计；
   - 资源不可控（全表扫描、笛卡尔积）。
3. 表关系与查找逻辑作为带 digest 的版本化数据（语义模型）记录与校验，思路与现行 table_rules 相同。
4. 查询在 backend 侧的按 commit 只读副本上执行，不给 Repository Service 增加通用查询接口。
5. 每个回答带出处：CommitId、语义模型 digest、查找逻辑 ID 与参数。

## 3. 现状依据

- Repository Service 的读取接口按 exact commit 整表流式读取（`/v1/repositories/{repository_id}/versioned/commits/{commit_id}/rows`，
  查询参数只有 `table_name` 与 `unknown_type_policy`），没有过滤、投影或连接。按条件查数据需要在 backend 侧另建一层。
- 总纲 §9 规定 Repository 不含 Workspace、Submission、Archive 等业务语义；跨表连接属于 backend 的职责。
- commit 不可变，History 树的每个节点都有 exact CommitId，因此按版本查询与按 CommitId 缓存都是安全的。
- 真实数据规模：最大的 `dbcfg.sql` 约 80MB（`/home/dev/gateway-real-dumps`，见[执行计划 §8.3](../plans/p5-arch-closure-execution-plan.md)），
  内存中的分析副本足以承载。
- 能力层是纯计算、经端口取数据的形态（见[分析能力工具化](future-ai-tool-exposure.md) §3.1），新增查询能力可以沿用。

## 4. 方案要点

### 4.1 语义模型

以结构化文件（YAML 或 JSON）记录，放在 Git 中评审。包含：

| 内容 | 要素 |
| --- | --- |
| 实体 | 对应的表；业务名称与同义词；键列；标签列（用户用来称呼它的列，如设备名、点名）；枚举码的含义 |
| 关系 | 起止表；连接列；基数（1:1 / 1:N）；附加条件；业务含义说明 |
| 查找逻辑 | ID；意图描述与问法例句；参数（有类型，并指定用于解析的实体）；执行步骤（经过的关系、过滤、输出字段）；输出形态 |
| 例题集 | 问题 → 期望的查找逻辑与参数 → 在某份真实数据上的期望结果；既是文档也是回归测试 |

三级校验：

1. 静态：格式合法；引用的实体与关系存在；无环或歧义路径。
2. 对照 schema：表与列存在，连接列类型兼容。对照的是存储规则视图（`StorageRuleView`），不是原始 SQL：被规则丢弃的列与
   SKIP 表不进入 Repository，查不到。
3. 对照真实数据：连接的孤儿率与选择度；例题结果一致。

辅助记录：可以根据列名相似性与值包含关系从真实数据中推断候选关系，由 owner 确认、命名并补充说明。S1 kickoff 的普查脚本
遍历全部表与列，可以顺带输出候选关系清单。

### 4.2 查询引擎与读模型

- 按需把指定 commit 的相关表经 Repository 客户端读为 Arrow，装入 DuckDB（或 Polars）执行过滤、连接与递归遍历。
- 以 CommitId 为键缓存；commit 不可变，缓存只按容量淘汰。读模型属于派生的临时状态，丢失即重建，不建立持久证明机制
  （[比例化保障政策](../policies/proportional-assurance-and-risk-based-verification-policy.md)）。
- 多跳遍历用递归 CTE 处理；暂不引入图数据库，出现大量不定深度的图查询且关系型执行明显不足时再评估。
- 数据变大时，可以只给 Repository 的 rows 接口增加列投影（业务中立）；不增加业务查询语义。
- 默认查询业务基线 head；`as_of` 可以指定 History 节点，与 comparison 组合即可回答“两个版本之间改了什么”。

### 4.3 MCP 工具

工具数量少、分层清楚；不为每条查找逻辑单独建工具。

| 类别 | 工具 | 作用 |
| --- | --- | --- |
| 发现 | `list_lookups`、`describe_lookup`、`describe_entity` | 查找逻辑、参数、实体字段与关系；描述来自语义模型 |
| 解析 | `resolve_entity(text, entity)` | 把用户的说法解析为候选键并打分；有歧义时由 agent 反问用户 |
| 执行 | `run_lookup(lookup_id, params, as_of?)` | 执行已登记的查找逻辑，返回摘要与第一页结果 |
| 执行 | `traverse(entity, keys, relation_path)` | 没有现成逻辑时，只能沿已登记的关系遍历 |
| 下钻 | `get_rows(result_handle, page)` | 分页取明细，单页有行数与字节上限 |

- 实体解析决定使用体验。设备名等标签多为中文长串，先用 n-gram 加拼音首字母检索，效果不足再加向量检索；检索只负责召回，
  最终键由规则或用户确认。
- 自由 SQL 工具如要提供，只作为管理员在沙箱中使用的只读工具，默认不开放。
- MCP 服务保持很薄、只做确定性处理；推理在 MCP 客户端的模型中进行，服务端可测试、可复现。

### 4.4 在架构中的位置

- 新 capability（暂名 `business_query`）：语义模型契约与校验、执行计划编译、在 Arrow 表上的执行；纯计算，经端口取数据。
- Application 用例：解析 scope → 确定 commit（默认基线 head，或指定 History 节点）→ 经读模型端口取表 → 执行。
- infrastructure：按 CommitId 缓存的读模型。
- 对外先提供 HTTP 路由，再由 MCP 服务作为 HTTP 客户端包装，与[分析能力工具化](future-ai-tool-exposure.md) §6 第 1 期的形态一致，
  不新增信任机制。
- 查询按用户对项目的 exact scope 授权；查询记录审计日志（调用者、时间、查找逻辑、参数、commit）。

## 5. 前置与约束

- 语义模型对照收口后的规范 schema 校验：S2a、S2b 之后列类型、键与规范形态才稳定；S3 之后 `logics.xml` 的组合信号才进入
  Repository，才能被查询。
- 只能查到已入库的数据。查找逻辑需要被丢弃的列或 SKIP 表时，要么修改存储规则使其入库，要么读取原始上传包；后者不是
  权威基线，结果须明确标注。
- 查询结果是只读的派生结果，不写任何权威状态，不作为提交、审核或归档的判定依据。
- 不暴露服务端路径；不把 Repository Service 直接暴露给 agent；AI 客户端经现有认证与授权（[分析能力工具化](future-ai-tool-exposure.md) §5.4）。

## 6. 建议节奏

| 阶段 | 内容 | 条件 |
| --- | --- | --- |
| 现在 | 定下语义模型的文件格式，开始记录关系、查找逻辑与例题（不写代码） | 无，与收口互不影响 |
| S1 kickoff 之后 | 用普查结果校验关系、生成候选关系清单；主机侧离线执行器（DuckDB + 真实数据）验证查找逻辑，只放在 `vnext/backend/benchmarks/` 等不进生产包的位置 | 普查完成；须在对应阶段的授权范围内 |
| P5 整体 exit 之后 | backend 查询用例、读模型与 HTTP 接口；MCP 工具 | 有确认的使用方；启动前写 ADR |
| 之后 | 改进实体解析；历史版本查询与版本间差异 | 按使用反馈 |

## 7. 待单独讨论的问题

1. “当前业务数据”的默认含义：业务基线 head（建议默认）、最新一次提交，还是未提交的上传版本；其他版本经 `as_of` 显式指定。
2. 使用者画像：熟悉表结构的工程人员可以开放更多遍历能力；一线业务人员以登记好的查找逻辑为主，配合反问消歧。
3. 是否需要跨项目查询；这影响 scope 模型与读模型缓存的键。
4. 回答形式：只返回数据，还是需要 agent 解释原因（后者需要语义模型记录更多业务说明）。
5. 语义模型的文件格式、存放位置与评审流程；例题集的规模与维护方式。
6. 实体解析的方案与评测方法；自然语言到查找逻辑的命中率如何评测（非确定性评测不进入普通 CI，定期运行）。
7. 与分析能力工具化的关系：两者共用 MCP 服务与认证方式，还是分开部署。
