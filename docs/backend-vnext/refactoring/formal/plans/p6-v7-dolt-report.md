# Phase 6 前置验证 V7：Dolt 回放与逐表读取

## 结论

- 三种回放的 312 张表哈希都与 t4 v2 相同。整表重建 312 张表用时 36.590 s；只重建 27 张变化表用时 16.199 s；对 25 张有主键变化表逐行发 SQL、keyless 表回退整表时用时 208.396 s。
- 实测的 12 张低变化有序表只有 0.1323% 行变化，逐行回放约 0.114–0.121 s/表，整表重建约 1.085–1.104 s/表。其余 13 张有主键变化表均接近 100% 变化，逐行 SQL 明显更慢。V7 支持表级跳过和阈值式回退的方向，但没有测到 0.1323% 与 100% 之间的交叉点；建议保留 1,000 行 / 5% 草案，作为保守策略而非已拟合的最优阈值。
- 按逐表耗时拼出的混合写入估算约 4.450 s，约占 V5 t4 Submit operation wall 的 0.8%；这是算术估算，不是一次完整混合 replay。全表重建和变化表重建分别约占 6.4% 与 2.8%。
- 单个已热 t4 commit 的 246,874 行 Arrow 读取，1/2/4/8 并发分别用时 73.751/55.447/34.871/26.691 s；8 并发为 2.76× 加速。16 并发触发 RS 的 503 拒绝，未排队。该测试不是 DC38 所要求的两节点、2× t4 冷读；H2 ≤ 5 min 草案仍有明显余量，但 V7 不能替代正式冷读验收。

### 阈值与 Submit 占比

实际 commit diff 有 27 张变化表、0 张 schema 变化表、2 张 keyless 表。12 张低变化有序表共有 117,864 行 parent / 117,936 行 target，实际变化等价行数 156；每表 13 个行级语句。它们逐行写总计约 1.417 s，整表重建总计约 13.166 s，约快 9.3×。13 张其余有主键变化表变化比例均为 100%；对它们逐行执行比整表重建慢得多，例如 parser 配置表为 81.978 s 对 0.529 s。keyless 的 `forwardtable_yx1` 与 `project` 都走整表 fallback。

D10 的原始 SQL 统计为 30 张变化表（12 张低变化、16 张近 100%、2 张 keyless），低变化表合计 63,936 行 / 156 行变化。V7 对 V5 保存的 v1/v2 commits 观察到 27 张（12 / 13 / 2），156 行低变化完全相同，但低变化表的行数分母为 117,864。V7 以规范化后的 commit/table manifest 和 Dolt diff 为准；它与 D10 一次性原始 SQL 普查的另外 3 张高变化表及行数分母差异，无法从这些 commit 快照解释，需在 Phase 6 设计中保留为数据口径差异，不能把 30 张统计强行套到回放结果。

0.1323% 与 100% 是本次有主键表观测到的两端；中间没有样本，无法精确拟合交叉阈值。维持 1,000 行 / 5% 草案可将这 12 张低变化表路由到 patch、将 13 张高变化表路由到重建；1,000 行条件本身没有临界样本可校准。全表重建的 36.590 s、只重建变化表的 16.199 s，以及按逐表结果替换 12 张低变化表成本得到的混合估算 4.450 s，分别约占 V5 v1 Submit 570.581 s 的 6.41%、2.84%、0.78%，占 v2 Submit 575.548 s 的 6.36%、2.81%、0.77%。混合值是假设 staged commit 成本与变化表重建相同的模型估算，不是整次 mixed replay 实测。对照 D10 引用的 S5 约 24 s 直接导入结果，V7 的整表 SQL replay 含 RS SQL 执行、Dolt add 与提交，测量边界不同，不应视为同一微基准。

## Repository Service 逐表 Arrow 读取

读的是 t4 v2 单个 commit 的全部 312 张表，共 246,874 行、约 44.6 MiB Arrow。并发档按顺序运行在同一服务与同一节点；每档均请求一次 catalog 并逐表读取。每表耗时分布为单表 rows HTTP 请求 wall；decode 与 `to_pylist()` 单独计时。CPU 为独立复测的 `/proc` 进程计数器边界差值，所以 wall/CPU 同一档但不是同一次请求序列。

1–8 并发共读完 246,874 行，无 HTTP 错误或行数不匹配。请求 wall 是主要耗时；单表 Arrow decode p95 小于 0.0003 s，Python 列物化 p95 约 0.027–0.030 s。8 并发使总 wall 降到 26.7 s，但单表 p95 随并发升高。16 并发两次补充运行分别有 296/295 个 HTTP 503，只有 16/17 张表成功；没有解码错误或行数不一致。RS 的 row-stream permit pool 容量为 8 且采用非阻塞 `try_acquire`，超出容量的请求被拒绝而不是排队。未把失败请求重试成成功结果。

CPU 边界复测为每档 RS 进程约 22–24 CPU s、Dolt 进程约 14–15 CPU s；16 档只处理了 17 张表，故两类 CPU 均小于 1 CPU s。容器进程在读取期间留下了约 1,899 个 `dolt` defunct 子进程，CPU 为零且不再活动；重复进程快照已确认它们污染了高频活动进程计数，因此弃用 100 ms 轮询版本，改用档位边界 CPU ticks。Compose teardown 后进程树消失。该子进程回收现象是 V7 的运行异常，未做产品改动。

## DC38 H2 与边界

- 单节点一个热 t4 commit 的顺序读取为 73.8 s；粗略线性折算 2× t4 约 147.5 s。8 并发一个 t4 为 26.7 s，2× 约 53.4 s。两者都低于 DC38 H2 草案 300 s，但只是同一已热节点上的容量参考。
- 该数据根此前经历回放和 Repository Service 启动，catalog 与 Dolt 文件缓存已热；本次没有清空 OS/Dolt 缓存，也没有两节点冷读、两个不同 commit 的双倍数据、或完整 History operation。不能据此宣称 H2 已通过冷读门槛。建议保留 ≤5 min 草案，到 DC38 指定的两节点 2× t4 派生缓存全 miss 测量后再判定。
- V7 读取验证的是 RS Arrow 列流与 Python 行物化，不包含 Backend 的 artifact 写入、checkpoint、Preview bundle 或 History comparison。它不能解释或替代 V5 的 `materialize_inputs` step 时间。
- 对照运行顺序固定且未随机化， replay 路径共享过本机存储缓存；每条路径一次。read 的 per-table JSON 首轮无 503，但两次测量重启间 OS page cache 未清空。数值适合指导策略与容量，不是冷启动基准。
