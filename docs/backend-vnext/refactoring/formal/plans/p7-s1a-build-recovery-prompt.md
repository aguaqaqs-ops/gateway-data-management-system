先检查原始错误，确认属于哪类，不预设“发生在 build 就是环境问题”：

- 命令/路径、获准缓存预填充、已授权本地环境或临时空间问题，且未改变程序逻辑、依赖选择、部署语义或预期：唯一执行者直接定位→修正→核前提→重跑失败步骤，不逐次转交实现/独审，也不要求执行稿双重评审。
- 需要改仓库构建脚本、Dockerfile、依赖/锁或 entrypoint 等源码：实施者修复，原审只对实际修订做一次针对性代码评审，再由执行者验证；后续纯命令/环境修正不重复评审，有新代码差异才审其差异。
- 程序编译/类型、运行时行为、产品逻辑或部署语义问题：正常实现/独审/测试流程，不伪装为环境故障。原因未明先只读诊断；无法确认副作用/安全收尾、需要新权限/他人资源或存在无法消解的来源冲突等真实阻塞时才交我决定。

确认属于非程序逻辑的构建条件/工具修复，修正复跑不设固定次数上限；每次要有具体修正、新诊断支持的方案或已核实环境变化，不无变化盲重试，不因达到 2–3 次机械停工。一个故障仅维护一个普通条目，追加根因、修正、每次结果及原始日志/exit/SHA 索引，最终 handoff 引用一次，不逐次新建报告和签署。既有失败保留，不补造证据。
