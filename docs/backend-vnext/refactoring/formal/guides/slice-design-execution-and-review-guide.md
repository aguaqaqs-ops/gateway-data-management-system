# 纵切与阶段设计、执行计划及独立审核指南

状态：参考指南；不新增 Contract、审批门禁或实现授权。

日期：2026-09-21。

适用：业务纵切、复杂功能或阶段性改造的文档落成与独立审核。简单修复无需套用完整流程。
来源：P5-5D 文档审核与 P5-5E 并行设计安排；具体业务决定仍由各自 Contract/设计拥有。

## 1. 与现有规则的关系

本指南说明如何把已有规则落实为可实施、可评审的文档，不复制其权威定义：

- [AGENTS.md](../../../../../AGENTS.md)：仓库硬约束及提交前检查。
- [Contract Taxonomy and Ownership](../contracts/contract-taxonomy-and-ownership.md)：语义 owner、依赖与变更责任。
- [Proportional Assurance Policy](../policies/proportional-assurance-and-risk-based-verification-policy.md)：风险、最小机制及验证取舍。
- [Testing Conventions](../../../testing-conventions.md)：测试入口、唯一 owner、容器重建和证据要求。
- [P5 Architecture Guardrails](../plans/p5-business-vertical-slices-design.md#p5-architecture-guardrails)：P5 增量架构约束；其他阶段按其 owning 规则执行。

会话中已明确的用户授权优先；不要凭本指南重新索取已有授权，也不要把路径整理、常规修复
升级为逐项审批。只有实质范围、业务语义或威胁模型变化才按已有 Contract/ADR 流程处理。

## 2. 先固定任务与事实

入口用简短说明记录目标、范围、实际 HEAD、工作区状态、文档版本、已授权动作和下一步。
明确区分四类信息：

| 信息 | 文档中的表达 |
| --- | --- |
| 已实现事实 | 指向真实源码/public port，并注明是否有相关运行证据；代码存在不等于验收通过 |
| 已接受设计 | 指向 accepted Contract/设计，明确尚未实现或尚未验证的部分 |
| 本次提案 | 明示 candidate、假设、依据及实际 consumer，不伪装成现有能力 |
| 执行证据 | 说明验证对象、范围、结果与限制；历史证据不能冒充当前候选结果 |

先读 owning Contract，再沿真实调用链核查源码、测试与必要历史记录。不要只凭名称推断接口，
也不要把作者的“已核查”或旧 handoff 当成当前实现证明。仅在缺失信息会实质改变核心方案时
提问；可逆的普通选择作明确假设后继续。实质未知项不得藏在“实现时再定”中。

## 3. 设计文档写到什么程度

设计应使未参与讨论的实现者能理解目标行为、依据与边界，并据此实施。按实际涉及的内容覆盖：

1. **业务与身份：**权威事实、派生结果、owner、稳定引用、业务关系及外部技术关系；
   成功条件、失败语义、权限和非目标。
2. **完整流程：**从生产入口、授权、输入解析、接受、执行/恢复到结果读取；
   不能只写领域模型，遗漏 worker、HTTP、装配、依赖或真实 consumer。
3. **一致性与生命周期：**事务边界、CAS、幂等指纹、重放顺序、并发语义屏障、
   必要的崩溃/响应丢失行为、结果与 artifact 保留。纯读查询无需硬套写事务模板。
4. **接口与资源：**public port、DTO、错误、digest/序列化语义、字节/数量/分页限额；
   caller 输入与内部事实的信任边界一致。
5. **现有接缝：**依赖的真实公共入口、已知阻塞、迁移/启动/重启影响、原 owner 的最小修复；
   “验收必须走通的路径”不能同时被排除在修复范围外。
6. **取舍与待决项：**核心选择为何满足当前 consumer/风险，什么变化需要重开；
   不为无真实需求的能力预建框架、状态机或证明体系。

按风险选择必要场景，至少贯通主路径与会改变核心结论的失败/并发路径。不要穷举内部步骤。
涉及上游语义变化时，列明冲突和最小替代方案，由 owning Contract 处理；补充候选与当前
accepted 版本分开表达，正式接受后同步状态及版本，不能通过下游设计静默修改上游。

## 4. 执行计划必须能兑现设计

按真实依赖划分阶段，不照搬其他纵切的阶段数量。每阶段简述以下内容即可，不建额外登记系统：

| 内容 | 应回答的问题 |
| --- | --- |
| 前置与目标 | 依赖哪些已接受语义、实际实现或验证？本阶段交付什么可观察行为？ |
| 路径预算 | 哪些生产/测试/配置路径必须新增或修改？必要的原 owner 修复是否包含？ |
| 验收 | 哪个唯一测试 owner 证明哪个业务不变量？使用什么实际可用的 focused 入口？ |
| 真实接线 | 何时验证 production factory、worker、部署输入和正式用户路径？ |
| 阶段结束 | 哪些证据交给独立 reviewer？哪些缺口阻止通过、哪些可延期到明确节点？ |

必改路径与有可复现缺口才启用的条件预算分开；不使用整层通配代替影响分析，也不把允许范围
细化成每个普通 helper 都需重新审批。未来测试文件可以列为交付目标，不能声称当前已存在。

执行计划写未来命令与期望证据；handoff 写实际执行结果。纯解析/校验不引入真实外部依赖，
同构错误用共享参数表。focused、最终权威 runner、五包静态检查及镜像触发点引用现有规范，
不复制多套门禁。最终容器结果绑定当前候选及实际运行 image identity。

## 5. 并行工作与独立审核

上游实现和下游 docs-only 设计可以并行，条件是下游可依赖明确的 accepted 语义，并记录
尚未实现的依赖及对齐节点。文档可提前准备不等于实现或最终验收可以跳过上游前置。

优先独立 worktree/分支，划分文档写入范围；共享 README、阶段总表等由明确一方合并更新。
不要混读不同时间的工作区内容后声称它们属于一个固定基线，不覆盖、stash 或提交别人的改动。
上游接口或语义变化后，对受影响依赖做差异复核，无需无理由重跑全部设计审核。

独立审核以固定文档版本和声明的代码基线为对象。已提交对象通常用 commit 即可；涉及
untracked/dirty 文档时，用明确文件范围和必要摘要补足定位，不为所有任务建立证据平台。
无法固定输入时说明限制，先取得可审核版本，不签署无法定位的 pass。

不同模型/agent 或新对话有助于减少沿用作者假设，但不是质量证明。审核者先验证核心模型与
完整执行路径，再看局部细节；不按作者身份、模型名、文档长度或沉没成本决定结论。

## 6. 审核结论：通过、定向修订或整体返工

| 结论 | 判定依据 |
| --- | --- |
| 通过 | 核心语义、架构、依赖、接口和实施验收成立，无阻塞性缺口；文档阶段不要求提前实现 |
| 定向修订 | 总体方案成立，有限章节或接口的修复即可解决，不必重建核心模型和主要执行路径 |
| 整体返工 | 核心前提、权威/权限模型、主要依赖或架构方向错误，或核心方案普遍缺失，局部打补丁无法形成可信执行计划 |

一个根本性问题足以支持整体返工；大量局部问题也未必需要整体返工。文风偏好、术语风格和
审核轮次不能替代上述判断。缺少关键外部决定时，应说明它阻塞哪些设计结论，不自动等同于
作者方案整体失败；通过中保留的实施前置必须显式记录，不能把未解决的核心语义包装成通过。

每项实质 finding 给出：文件位置、Contract/源码依据、触发场景、业务或实施影响、最小修正方向
和关闭标准。区分已证实缺陷、待验证假设与非阻塞建议；没有发现问题时直接说明，不凑数量。
基础权限、输入、资源、跨 scope、事务/CAS 等边界仍须检查，不能借“比例化”跳过。

判定整体返工时，报告聚焦少量决定性证据，解释为什么局部修补不足，列出可保留的事实、
应废弃的设计前提及重新设计的最小输入/验收目标。停止展开依赖错误架构的枝节补丁清单。
更换模型重新设计是可选措施；无论是否更换，重写后都按相同标准审核。

## 7. 修订、接受与交接

修订者说明每项 finding 的处理、相关章节变化和待验证内容；不把自己的自查冒充独立复审。
复审检查原 finding、改动传播及新增冲突，已关闭且未受影响的问题不反复重开。整体重写时
重新审核核心方案，可复用仍成立的源码事实与证据，不自动继承旧方案的通过结论。

最终清楚区分以下事件：

- 文档审核通过：接受设计及执行计划。
- Contract 补充接受：按 owning 规则更新语义、版本及引用。
- 实现授权：允许在明确范围内修改源码/测试/部署。
- 阶段或 slice 验收：基于实际实现和运行证据判断交付。
- Git 提交、发布及 production deployment：各自依照已给定授权执行。

这些事件可在用户明确授权时一起处理，也可分开；不要从一个事件自动推导全部授权。
用户已授权“条件满足直接接受”时，复审确认条件满足后直接落状态，不重复询问。
更新入口、正文、状态字段和独立记录，清除残留的“待接受/前置未满足”表述，保留必要历史。

## 8. 最小交付与后续任务引用

复杂纵切可使用 entry brief、detailed design、execution plan 三份文档；较小阶段可合并，
不要求固定文件数量。独立报告记录结论、审核对象、findings/关闭情况、剩余前置及验证限制。
无需重复抄写本指南或历史任务的完整提示词。

后续任务提示词只需补充以下任务专属信息，并链接本指南：

```text
目标与交付范围：
固定基线与工作区：
权威 Contract / 上游已接受设计：
必须核查的完整用户路径：
并行任务、依赖及对齐节点：
允许修改的文件 / 明确非目标：
授权动作（编写、审核、接受、实现、提交等）：
交付位置与检查要求：
审核允许结论：通过 / 定向修订 / 整体返工；依据本指南，不预设结论。
```

docs-only 落成检查链接/锚点、源码路径、版本/授权状态及差异范围；不为文档编写提前执行
实现测试或镜像构建。提交前检查仍按 AGENTS.md；报告实际执行过的检查，不借用别的工作区
或旧候选结果。指南本身不改变任何现有 slice 状态，也不构成未来任务授权。
