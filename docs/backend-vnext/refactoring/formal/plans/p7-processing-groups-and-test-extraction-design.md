## 1. 本轮确认与范围

Owner 已同意把设备分组边界设计清楚，并提出设备抽取默认包含全部历史、审核和未完成任务，通常用于单个设备测试/故障复现，无需选择个别历史或审核记录，也不需要将测试副本的后续修改合并回源环境。本文据此采用**设备全状态、单向测试副本**设计。

Owner 已确认本阶段安排，并授权下一编码会话 S1a A–G 至本地 exit；独立处理组/抽取工具的产品实现和部署仍不在该授权内。三份 S0 工作区文档已同步分组/阶段边界；“共享 control DB/存储”明确为组内共享，组间独立，不把两种部署解释同时作为实现依据。S1a 的默认单组、单 worker 验证范围不扩大。

继续限定单机、本地存储、同组织受控部署。首版采用静态设备分组；改变生产组归属在排空后进行。测试副本不改变源设备归属，不等待源设备转交写入权，不承担备份/长期留存承诺。无需引入多机、在线自动搬迁、双向复制或通用分支合并平台。

## 2. 处理组是什么

一个处理组拥有一组设备的业务执行状态及数据，是可独立启动、停止和配置资源的运行单元：

```text
生产环境的设备路由目录
  ├─ 设备 A、B → 组 1：backend + worker 池 + RS + 本组 DB/数据卷
  └─ 设备 C   → 组 2：backend + worker 池 + RS + 本组 DB/数据卷

设备 A 的单向抽取包 → 独立测试环境：一个 worker + 必要服务 + 独立 DB/数据卷
```

“独立测试 worker 能加载”定义为无需访问源环境状态即可加载和处理；worker 仍依赖本地 control DB、Repository Service、Dolt 和 artifacts。提供统一启动配置可以隐藏服务组装细节，不要求把全部服务装进一个容器，也不能让测试 worker 连回源 RS 来补依赖。

组内 worker 共享本组 control DB、RS 与各类 root，沿 S2/S3 分配不同设备的任务。不同组不共用可写 DB、Dolt 目录或 artifact root；相同宿主介质可用互不嵌套目录，物理磁盘带宽仍然共享。配置不同组的 CPU/内存份额可以隔离重任务；组内调度负责日常负载分配，组间静态调整不冒充在线自动均衡。

一台生产设备在同一环境下只有一个有效处理组。外部稳定设备身份不随换组改变；现有 `business_project_id` 授权 scope 和 repository 绑定继续有效。测试环境使用新 `environment_id`，可以保留原设备、repository、operation、submission、commit 和 artifact ID，靠环境隔离避免冲突，不为复制而重写所有业务引用。

## 3. 轻量共享目录的责任

共享目录只维护 `(environment_id, device_external_key) → group_id`、启停状态及 assignment revision；组的服务端点由部署配置登记，凭据不放表内。现有设备→repository/scope 映射继续由所属组的业务边界维护，目录不另存一份可独立修改的 Head/审核/任务完成状态。

目录在设备注册、停用和组归属变更时更新，普通比较/提交无需逐步写目录。路由可缓存，但请求必须带可核对的设备归属，接收组再次检查设备属于自己；旧路由不能导致旧组继续写入。单机实现可复用标准 SQL 事务/CAS，无需引入一致性服务。

目录不可用时不新建或转移归属；已经明确归属的组内工作可以按有效静态配置继续，外部不能靠猜组投递。先不承诺跨组一次事务、全局精确任务队列或原子全局业务查询。跨组统计按环境/组聚合各自只读结果，记录完整性。

生产换组属于写入责任转交：暂停设备新受理、排空或查明未知 effect、停用旧组该设备写入入口、迁移完整状态、核新组、CAS 切换目录后恢复投递。此流程与测试复制分开；测试复制从不修改生产目录，也不提供合并回生产的入口。

## 4. 默认抽取内容

用户只选择设备，首版不提供 history/review/pending 的勾选组合。导出器按当前 schema 的显式 owner 规则收集目标设备全部现存业务记录，再补全引用依赖；不是让用户指定 SQL 或任意路径的通用导出器。

| 内容 | 默认范围 |
| --- | --- |
| 设备映射与业务 scope | 目标设备映射、repository 身份、INITIAL/全部 baseline nodes、当前 Head |
| Dolt | 对应 repository 的完整现存库，包含保留历史、分支/refs、working state；不只导出当前表或最新 commit |
| 上传与 Workspace | 全部现存 Workspace、upload revisions、输入模式/关联、上传幂等记录、原始 package 与 provenance |
| Preview/History | 全部现存结果、比较接受记录、bundle/READY closure 及其现存成员 |
| Submit/审核/归档 | 所有 Attempt、Submission、occupancy、review events/projections/idempotency、disposition、archive plans/results/confirmation/anomaly records |
| 未完成及已完成 operation | 全部关联 operation/step、状态、重试次数、期限、诊断、checkpoint、prior outputs、固定 package/key、Repository operation 关联；不只复制 QUEUED |
| RS 状态 | 对应库的 registry、mutation/idempotency/effect、import operation/recovery、artifact lifecycle/pin/清理状态和关联现存文件；用于判断已提交但未应答的 effect |
| artifacts 与保护 | 从业务/运行记录、closure、cache/index 得到的全部关联现存对象和 protection/uses；同 ID 在包内只复制一次，分类位置不变 |
| 规则与配置 | 源程序版本、schema/profile 版本、实际 ruleset/配置身份及可取得的相应内容；资源参数作为原始条件保留，目标环境显式选择实际预算 |
| 已有诊断资料 | 可归属的现存日志、任务摘要/曲线、临时目录清单及可取得的故障残留；标为诊断材料，不作为恢复权威 |

“全部”指**抽取时源环境仍保留的全部目标状态**，不承诺恢复已经按原策略删除的文件、历史日志或曲线。不能以本需求为由禁止今后的合法 TTL/清理，也不自动抓取外部系统未落在本地的全部原始档案。已有 dangling ref、损坏/缺失字节也记录下来；故障现场不能为了通过导出而补成成功状态。

原进程内存、线程、文件锁、socket 和正在执行的 CPU 指令不属于可迁移任务状态。需要该类现场时另做专项诊断；本方案不使用进程 checkpoint/restore。能够从包启动不等于能精确重现原来的时序、负载和硬件故障。

## 5. 抽取依赖，而非人工选择历史

现有 control DB 中并非每表都有 repository_id，且多个 job/closure 通过 JSON/ref 关联；不能用一个 `WHERE repository_id = ...` 完成抽取。实现时由各 owner 提供按设备枚举记录/依赖的窄接口，按 schema 固定表清单覆盖 Workspace、operation、Submission/Archive 和 cache/protection；不建设可执行任意关系规则的图引擎。

核心规则是完整保留业务聚合：operation 与 steps、Submission 与审核事件、archive plan/result 等不能只复制其中一半。RS 的提交结果与 backend 对它的未定认知也同时复制，避免丢掉幂等/effect 证据后产生重复提交。

如果设备 A 的某次比较引用设备 B 的输入或快照，自动复制该历史执行所需的 B 依赖。稳定内容依赖可仅带引用的对象/完整库依赖；若 owning Contract 要求一个不可拆的业务聚合，则完整复制该聚合并列明依赖设备。不得截断引用来维持“包里严格只能有 A”的表面条件，也不默认递归复制 B 的全部无关历史。

目标设备是本次测试的可写业务范围；因依赖补入的其他设备不自动加入可领取任务/可写 scope。加载器与 query/claim/RS 接线核对该范围。若某个未完成任务本身需要同时写入未选设备，保留完整现场但阻止自动执行，并明确报告需要扩大测试范围；首版不静默扩大写入权限。

不同组间不建立共享可写 cache。相同内容在不同组/测试环境可有独立物理副本；清理和统计按 `(environment_id, group_id, service_owner, artifact_id)` 区分。设备级关联缺失的孤儿只能列为未知诊断材料，不能宣称已精确归属该设备。

## 6. 一致捕获与导出

先支持维护窗口内的静态捕获。为保留未完成任务，不要求把目标队列全部执行完；停止新受理和新 claim，按正常停止/故障处置路径停止相关 writer，记录截止状态。若停止期间某个任务完成，导出的是停止后的真实状态，不回写成先前 RUNNING。原现场已经停止时，不为导出先启动恢复。

由于 backend DB、RS DB、Dolt 和多个 artifact root 不是一个事务系统，首版在**源处理组全部 writer、cleanup 和维护任务停止**后捕获一致集合；组内其他设备暂受此维护窗口影响。不能只暂停 A 的 worker 就宣称共用 DB/RS 得到一致快照。拒绝“先复制 backend DB，源继续提交，稍后再复制 Dolt”的混合时点包。

对稳定集合用既有锁/SQLite 一致复制能力及标准文件复制或平台快照完成暂存；有可靠平台快照可缩短停服窗口，但不要求先建设快照平台。没有该能力时保持停服到所需源数据复制结束。后续筛选/打包在本任务暂存副本上完成，不删除或改写源 DB 行，不 GC 源 Dolt，不释放源 protection。

导出文件由 owner 枚举，限制在已验证 roots 内，不跟随 symlink/任意外部路径；复制过程分块、有界且检查目标空间。包带一份普通索引：来源版本/schema、捕获时间、目标/依赖设备、分类文件清单与大小/SHA256、缺失/损坏/省略原因、抽取工具版本。索引服务于完整性检查和加载，不是业务完成 receipt 或新持久状态机。

源本身不完整时，可以保存诊断包；索引明确区分“传输完整”与“业务恢复前提满足”。损坏不能被误报成正常可续行副本。导出失败不改变源设备归属或业务状态；仅清理本任务创建的目标暂存。

## 7. 加载与未完成任务

抽取包保存为不可修改的原始副本，每次实验创建独立可写运行副本。默认保留原业务 IDs、审核 actor 标识、checkpoint、状态、期限和固定请求 key，便于对照日志；历史 actor 标识不附带可登录凭据。

加载顺序：核包内容/schema/规则与目标程序版本 → 创建新环境/组及本地凭据 → 导入本地 DB、Dolt 和分类对象 → 核引用和 allowed-device scope → 启动目标 RS 与所需控制面 → 启动一个新身份的测试 worker。校验/导入未完成时不启动 scheduler、自动回灌或 cleanup。源 secrets/session/token、生产服务 URL、旧 PID/socket/锁持有关系不复制为有效运行配置；所有 effect 只能指向测试组本地 RS。worker 无源可写卷，也不携带源访问凭据。

| 源任务状态 | 测试副本行为 |
| --- | --- |
| QUEUED / RETRY_WAIT | 保留排队/重试条件，由普通调度领取；不人为增加 retry budget |
| RUNNING、原租约尚未过期 | 不复活原进程/worker 身份，不把状态直接改 QUEUED；按既有租约到期及恢复路径处理，必要时先保持 retryable startup block |
| effect 结果未知 | 查询复制后的 RS operation/effect 与 Dolt 状态，再沿正常 recovery 处理；不能只清 lease 后重放 import |
| PREPARED/frozen input 不全 | 保留稳定失败和诊断；不为“可加载”从别的版本重建冻结事实 |
| MANUAL_RECOVERY_REQUIRED、预算耗尽、绝对期限已过 | 保留原状态/期限和正常启动阻塞结果；不隐式延长期限或跳过恢复门禁 |
| SUCCEEDED/FAILED/CANCELLED 等终态 | 保留历史及关联数据，不自动重新执行；复测通过正常的新测试操作表达 |

首版不新增“复制任务特殊恢复算法”，默认等待原有限租约自然失效并使用既有 recovery。如果开发者需要修改时钟/期限/状态来触发某个故障路径，这是运行副本中的明确实验，必须与未修改原包区分，不把修改后的结果称为原状态恢复。普通新任务/提交只改变测试副本，可以多轮实验，但没有回合并入口。

“可加载”的验收是包可解释、原状态可见、引用可解析、必要依赖本地可达，且符合恢复前提的任务能由正常 worker 恢复；源已有的故障仍可导致 worker 正确拒启。不能同时要求“保留所有故障状态”与“任何包都保证 readiness 成功”。抽取内容中的业务状态持久化齐全也不代表时序故障必然重现。

默认先用源版本运行包。采用开发代码时，代码必须能读取同一 schema/Contract；不自动 migration 或删 DB 以获得启动成功。确有 schema 改动的实验单独准备转换后的运行副本并保留源包，或者重新导入输入；本轮不承诺任意历史版本到任意开发版本兼容。

## 8. 对 S1a、S1b 与后续阶段的影响

| 范围 | 设计约束 |
| --- | --- |
| S1a root 布局 | 十个 slot 均属于某个处理组；组内共享、组间隔离。容器路径可相同，宿主 source/volume 必须独立；不增加每设备任意选盘 |
| ArtifactRef | `a1:<location>:<token>` 继续只表示组内逻辑位置，不加入物理路径或目标组 ID；调用上下文决定环境/组。单向复制可以保留 ID，不建立远程 artifact resolver |
| 资源预算 | 组内 W/K 沿原含义；整机检查各组 `W×E` 以及各组 backend/RS 和宿主共享余量之和。测试组也占实际资源，不因是调试用途跳过预算 |
| S1b 归属 | 摘要/查询带环境与组，来源设备与测试副本分别统计；副本字节是真实额外占用，不能按 ID/SHA 跨环境去重后少算 |
| S2a 恢复 / S2b 组隔离 | 组内原子 claim、lease/CAS、固定 package/key 不变；S2b 验证静态目录、两组状态/资源隔离；测试副本先完整携带 RS 再恢复，生产旧 worker 不参与测试租约 |
| S3 调度 | 组内设备公平/交互与批量策略；先不建跨组在线调度器或全局槽位数据库 |
| S4a 入口 | 设备路由与组内映射责任分开；测试加载不注册/切换生产目录；回灌客户端显式绑定环境 |
| S4b 抽取 owner | 新增受控离线导出/加载边界，明确各 DB 表及文件 owner；不把通用 RS whole-root snapshot CLI 当作现成单设备抽取能力；排空生产换组与测试复制分别处理 |

源码复核显示：backend `schema.py` 包含独立 Workspace/operation/审核/归档/cache/protection 表，关系不是单一 repository 字段；`worker_startup.py`/`recovery.py` 实际检查租约、预算和恢复能力。RS `snapshot_admin.py` 当前提供的是静止 whole-root hold/check，不负责按设备筛选、复制或跨版本转换。这些是后续实现需要补齐的工作，不能宣称现有工具已完成设备抽取。

本补充不把所有功能塞进 S1a。阶段安排已确定：S2b 在原 S2a 验收之外增加组隔离，S4b 在原 S4a 回灌验收之外增加抽取/加载；各自工具接口、schema 映射和受影响 Contract 在该子阶段实施前细化。S1a 的退出范围保持单组单 worker。新增设计不改变 P6 的退出结果或当前恢复缺陷的既有记录。

## 9. 最低验证责任

未来实现时按 AGENTS 在专用节点、隔离资源和 clean 已提交源码上验证；本轮不执行。

| owner | 必须证明 |
| --- | --- |
| 抽取/加载 | 一个设备有多轮历史、完整审核/归档、所有终态及未完成任务时，默认整体导出，无需人工选子记录；记录关系和必要引用闭合 |
| 源一致性 | backend DB、RS DB、Dolt/产物来自同一静止集合；导出不修改源状态/归属，不要求把所有 pending 跑完 |
| 恢复 owner | QUEUED、未到期 lease、effect 已完成但 backend 未知、PREPARED 缺输入、manual/deadline 代表场景保留正确语义，不重复提交或绕门禁 |
| 隔离 owner | 测试改动源不变、源继续工作测试不变；凭据/端点/卷/清理完全隔离；依赖设备不被误领取或写入 |
| 存储 owner | shared artifact 在包内去重，跨环境独立存储；多 root 同盘/分盘可加载；缺失/损坏事实不被悄悄修复；超容量有界失败 |
| 版本 owner | 源版本可加载正常包；不兼容 schema 明确拒绝；原始包保持不变，可重新生成实验副本，无回合并动作 |

每个场景沿既有 owning 测试扩展，不新建重复全故障矩阵；跨 DB/文件一致性和容器隔离需要实际集成验证，静态表清单不能替代。包保存不保证精确时序故障复现，报告保留其运行条件。

## 10. 结论与本轮状态
