# P7 整顿后的阶段设计入口

日期：2026-11-12。依据 [S0 §19 决议](p7-s0-owner-decisions.md#19-后端专项整顿与后续阶段收窄2026-11-12)及 [专项整顿计划](p7-backend-remediation-execution-plan.md)。本文收录已确认设计输入，详细接口/参数在对应阶段定稿；不授权本轮实施 S3–S5，不变更 S2b 已有范围、角色、执行计划或验收记录。

顺序：S2b exit/main → 四批整顿 → S3 → S4a → **立即小规模真实回灌演练** → S4b → S5。演练发现的产品问题优先处理，S4b 可让路。L5 是否启动待试点报告及 Owner 决定，此处不预排第二轮。

## 1. S3：有界、两类任务、简单保底

P7-D15 不变。首版只包含上传、持久队列、executor、RS 各层的有限容量与明确拒绝原因；交互与批量两类、一个简单批量保底；排队期间期限语义与输入保护；磁盘低水位；批量暂停开关。不抢占运行中事务，不用无限重试维持受理。

- 设计接点：`operations/` 领取与 deadline、`infrastructure/control_db/sqlite_operations.py`、HTTP 上传准入、`application/` 用例入口、RS reader/writer 资源限制及现有磁盘检查。
- 定稿一个可验证的保底方式及有限参数，不预选设备公平/aging/复杂优先队列。P7-D22 真实数据取舍规则适用；只有回灌或试运行显示**同类任务间饥饿**才重开设备公平和 aging。
- 明确排队期限与执行预算、输入 TTL、取消/恢复的关系；维护不擅自暂停原期限，不把资源拒绝计为成功样本。整机预算计所有组及共享服务，仍组内领取、无跨组调度器。
- 最小验证：交互优先与批量持续可进展、队满/磁盘低/排队过期/暂停取消、输入保护及释放、同设备历史不乱序；既有事务/CAS/UNKNOWN 恢复继续有效。
- 前端可见排队原因/状态 DTO 在阶段总结写明提交与语义，由 Owner 转交；退出核前端按新接口的真实 backend 旅程，不直接通信或在后端整顿中改前端。

## 2. S4a：有序回灌与按需批量新增

继续 P7-D01、D04–D10：外部系统提供稳定设备身份、版本识别和排序；本系统沿正式 Preview→Submit→Review→Archive 处理。正常版本自动审核归档，异常停止本设备基线推进，其他设备继续；重复输入/响应丢失/中断续行及独立样本分析沿现有业务边界。

批量新增的接点为 `vnext/scripts/processing_group_entry.py` 的逐设备新增、目录发布与 Nginx reload，及 backend 组内设备注册。**触发后才做**：首批接入或回灌实测逐个新增耗时、或上一代 worker 未退出导致 busy，已构成实际问题。记录设备数、耗时/busy 与在途请求条件，比较“一次准备多个设备、一次发布”能否解决；无需新服务。

触发后的详细设计保持先准备目标组映射/授权再开放路由、同身份幂等、冲突拒绝及失败不伤既有设备；明确部分准备失败的发布集合与重试查询，不默认跨多个 DB 原子事务。S2b 的逐个热新增实现与其验收不回改；程序/资源/root 变更仍仅相关组维护，已有设备迁移不伪装成新增。

### S4a 退出后立即演练

Owner 已确认外部系统能提供若干设备的完整历史。演练使用真实设备身份与每设备完整有序历史，包含版本数量、输入摘要/来源、权限、资源预算、节点/部署环境及可重建边界的具体清单在执行前一次确认。不能拿改名的同一数据充多个真实设备。

复用回灌客户端与已有统计，每尝试保存 P7-D23 的输入形态、阶段耗时、缓存计数和有界按表数组；记录正常/无变化/异常停链、失败和重放，结果不能因统计写失败改变。用这些数据判断缺陷、真实主要耗时、S3 饥饿重开条件与批量新增价值，不新增采集平台或大规模性能矩阵。先修暴露的问题，再推进 S4b；不等待 S5 才让成批真实数据经过全链。

## 3. S4b：测试副本三步阶梯

收窄 P7-D18、P7-S2-D09 和 P7-D19 的 S4b 交付承诺；P7-D17 的独立处理组、统一入口/目录与 S2b 热新增仍保留。**受控生产换组移出本轮**，以后有真实需求再定，不能把旧设计的 S4b 标签当授权。

| 阶梯 | 触发与范围 | 设计与验收底线 |
| --- | --- | --- |
| 1，首版必须 | 整组克隆，加“只领取指定设备任务”的测试配置 | 源组全部 writer/cleanup/维护停止后，以标准文件/SQLite 一致复制取得 backend DB、RS DB、Dolt、全部 roots 的同一集合；未完成任务不必跑完。新环境/凭据/端点/卷隔离，不连源服务、不复用生产 secrets；在 claim 前过滤 allowed-device，先明确无设备 scope 的维护/未知任务处置。验证未选设备不被 claim/effect，缺失/PREPARED/UNKNOWN/原期限按既有规则，不伪造健康 |
| 2，条件触发 | 整组克隆的时间或磁盘成为实际问题才做部分克隆 | 先给实测问题及收益，标准复制/按已知 owner 筛选足够则不建通用关系引擎；保留引用闭合、共享依赖与未完成状态 |
| 3，条件触发 | 确需把单设备最小完整包带到别处才做设备完整抽取 | 按显式表/文件 owner 枚举全部现存历史、审核、未完成任务及必要依赖；无历史子集选择器、任意版本转换、双向同步或回合并 |

接点：`worker` claim、`sqlite_operations.py` 与 scope 解析、部署 storage layout/资源 profile、RS `snapshot_admin.py` 和 SQLite/文件复制。RS whole-root 管理能力不等于已有完整组克隆或单设备抽取工具，需核 backend/RS/roots 一起静止。首版不为阶梯 2/3 预建包格式或导出框架。

既有[分组与测试副本设计](p7-processing-groups-and-test-extraction-design.md)的身份、数据隔离、一致捕获、原状态恢复及跨版本拒绝是底线；按设备闭包算法只在阶梯 2/3 触发后细化。allowed-device 是测试执行范围，不代替应用权限，不能放开跨 scope 写入，也不能让整组克隆变成生产归属转交。

## 4. S5：统计的事后检验

按 P7-D22 第 5 条检验现有 S1b 实现，**现在不撤销** P7-S1B-D03 的 1 秒采样/7 天曲线或 D04 查询/导出，不重开 B6/B8。S5 准备试运行的消费核对清单、观察期间和责任人，试运行后给结论；S5 不因“尚无足够观察期”虚报零调用或无限等待。

- 接点：`http/routes/statistics.py` 的三个曲线端点、`statistics/queries.py`（整顿后经 application 用例入口）、`infrastructure/statistics/` 的 `resource_samples` 写入/保留与摘要峰值计算。实施设计时复核真实路径，按实际调用跟踪，不只搜索前端 import。
- 用现有访问记录与消费者确认判断是否查询，不新建计量/监控服务；内部测试、健康探测不充业务消费者。证据缺失写未知，不直接判无人使用。
- 试运行期间确无曲线查询：停止逐样本落盘，保留摘要需要的峰值，删除样本表和三个曲线端点及专属测试/配置；作为后续有据变更同步 Contract/OpenAPI/消费者和门禁，不在整顿冻结内提前删除。
- 消费者确定前只读查询接口不承诺稳定，不再增加端点；试运行后未调用的端点列删除候选。仍保留版本化 DTO、授权、分页/导出有界和统计失败不影响业务。
- D24 的 t4 参考/N2 核对在整顿闭合，S5 核收其适用性及之后的变更，不再次顺延。Preview 优化保留 S0 §18 的“先实测再讨论”，不恢复强制双 pair 并行。

## 5. 下次文档变更时处理的空 GID 引用

前端目前用 `logical_path` 是否含 `/blank/` 识别空 GID。下次修改 surface 或 bundle 文档时，由 owning Contract 提供 blank 记录显式引用并同步消费者；现在不单独改格式或 golden。接点为 surface/bundle 文档构造与前端对应消费者（仅只读核对）；后续阶段总结经 Owner 转交前端，不在本轮新增接口。

## 6. 首次保留数据的部署准备

Phase 8/9 以 [implementation-stages §11–§12](implementation-stages.md#11-phase-8首次保留数据的部署准备)为入口：前向 migration、备份恢复、正式认证、前端静态文件经统一入口发布、运维及 Dolt 升级流程。没有在用旧系统，不要求 shadow、双重验证/流量切换、feature flag 回滚或删除旧 Flow；若未来确有替换对象再重开。当前单一基线与可重建试运行不自动获得保留数据部署承诺。
