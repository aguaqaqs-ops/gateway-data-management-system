# 设备目录系统设计（试运行版）

状态：owner 已确认，2026-11-11（Q1–Q5 见 §11）。接口细节见 [interfaces.md](interfaces.md)，草图见 [sketches/](sketches/)。

## 1. 目标与范围

设备目录是独立于网关机数据管理系统（下称“网关系统”）的一套小系统，作为试运行阶段进入网关系统的入口：

- 按 地区一 → 地区二 → 项目 三层浏览，或按项目名、站号、拼音首字母搜索；
- 选中项目后跳转到网关系统中该设备的数据提交树，之后的上传、Preview、提交、审核、历史比较都在网关系统内完成；
- 目录名单由外部程序导入，目录系统为每个项目生成设备唯一键。

**不做：**权限系统；一个项目多台设备；在目录中显示提交、审核等状态；正式 SSO；规模评估。这些放到正式运行阶段再决定（§10）。

**与现有网关系统原则的关系：**网关系统中“一个会话对应一个网关设备与业务项目、切换设备即切换会话”（前端 kickoff §4.3，FD2）不变。目录系统负责为每个设备签发会话，“切换设备”就是回到目录、换一个设备重新进入。

## 2. 已确认的业务约束（owner，2026-11-11）

| # | 约束 |
| --- | --- |
| B1 | 目录系统与网关系统相互独立：独立的前端与后端，尽量简单 |
| B2 | 不设计权限，所有人都能看到全部项目。以后的权限系统也独立于网关系统，网关系统自身不做身份认证 |
| B3 | 主要使用者是审核人，但试运行要能走通上传、浏览、审核的完整流程 |
| B4 | 项目名可以重名。站号视为全国唯一且不会变。设备唯一键在试运行阶段由目录系统自动生成，正式运行时改由其他系统导入 |
| B5 | 地区和项目名单由外部程序导入，目录系统只约定导入规则 |
| B6 | 搜索字段为项目名、站号、拼音首字母；拼音由导入方提供 |
| B7 | 目录中有、但尚无数据的项目照常显示；进入后提示“尚无数据”，保留上传入口 |
| B8 | 默认按名称排序 |
| B9 | 试运行只用一个身份 `test1`，会话有效期设长一些 |
| B10 | 试运行阶段与网关系统部署在同一台机器 |
| B11 | 规模：约 8 个地区一，每个地区一下 20–30 个地区二，每个地区二下几十到几百个项目；暂不做完整规模评估 |

## 3. 总体结构

```
 外部导入程序 ──CSV──▶ ┌────────────────────────────┐
                        │ 目录命令行（运维）           │
                        │  import    导入目录名单     │
                        │  provision 开通设备         │──┐ ① 在仓库服务建仓库（compose exec）
                        └────────────┬───────────────┘  │ ② 停 backend/worker
                                     │ 读写               │ ③ 写 设备映射文件 + 会话文件
                              directory.sqlite3           │ ④ 启 backend/worker，等 /readyz
                                     │ 只读               ▼
 浏览器 ──▶ 目录服务（HTTP，单进程）                网关系统（Compose：backend / worker / repository-service）
           ├─ 目录前端（静态文件）                         ▲
           ├─ GET  /api/catalog                            │ Bearer token
           └─ POST /api/handoffs ──▶ 跳转地址 ──▶ 网关前端（片段携带会话）──┘
```

- **目录服务**只读自己的 SQLite，运行时不写网关系统的任何文件，也不调用网关接口。
- **目录命令行**是唯一会碰网关系统的部分，且只通过三个已有接点：仓库服务的建仓接口、设备映射文件（`GATEWAY_BACKEND_PROVISIONED_MAPPING_FILE`）、会话文件（`GATEWAY_BACKEND_SESSION_FILE`）。
- **网关前端**需要补一个小入口：从跳转地址中读出会话（§7.3）。这是网关系统唯一的代码改动，位于 `frontend/`，不涉及 `vnext/`。

**代码位置：**仓库根目录新建 `directory/`（服务、命令行、前端都在其中）。不放进 `vnext/`，避免改变后端测试闭包与镜像身份；也不放进 `frontend/`，保持与网关前端相互独立。

## 4. 数据模型

目录 SQLite 中三类数据：

| 实体 | 字段 | 说明 |
| --- | --- | --- |
| 地区 | 地区一名称、地区二名称 | 以名称路径为标识；改名视为新地区（试运行可接受） |
| 项目 | 站号（主键）、项目名、地区一、地区二、拼音首字母（可多个）、全拼（可选，可多个）、设备键、项目号、是否已移除 | 站号决定设备键；项目改名、换地区时设备键不变 |
| 开通记录 | 设备键、仓库 ID、初始提交号、初始基线节点 ID、会话 token、会话到期时间、开通时间 | 只在 `provision` 成功后写入；同一设备只开通一次 |

另记一条目录元数据：目录版本（导入时生成）、导入时间、导入文件 SHA256。

**唯一键（B4）：**由规范化后的站号确定性生成，同一站号在任何时候、任何机器上生成的键都相同。规则见 [interfaces.md I2](interfaces.md#i2-唯一键规则)。键不含名称和地区，所以改名、换地区不影响已开通的设备。正式运行时键改由其他系统导入；按项目前提，届时直接改为新规则并重建试运行数据，不做兼容。

## 5. 导入（B5）

- 格式为 UTF-8 CSV，字段与校验见 [interfaces.md I1](interfaces.md#i1-目录导入文件)。
- **整份替换：**每次导入都是完整名单。校验全部通过才生效，任一行出错整份拒绝，并逐行报告错误。
- 站号重复、必填字段为空、拼音格式不合法、生成的设备键冲突，都会拒绝。
- 名单中消失的项目标记为“已移除”：目录中不再显示，开通记录与网关系统中的数据都保留；以后重新出现时恢复。
- 导入结束输出摘要：新增、更新、移除、恢复、不变各多少条。
- 支持 `--dry-run`，只校验并输出摘要。

导入只改目录自己的数据，不触碰网关系统，不需要重启任何服务。

## 6. 开通（provision）

网关系统只能进入已在设备映射文件中登记的设备，因此“导入到目录”与“在网关系统开通”是两步：

1. 选择要开通的设备：指定站号列表文件，或 `--all` 开通全部未开通项目。B11 暂不评估规模，建议按试运行实际需要分批开通。
2. 对每个未开通的设备，在仓库服务创建一个空仓库，拿到仓库 ID 和初始提交号，立即写入开通记录。
3. 停止 backend 与 worker。
4. 重写设备映射文件和会话文件：保留不归目录管理的条目，为全部已开通设备写入映射与 `test1` 会话。
5. 启动 backend 与 worker，等待 `/readyz` 就绪。

**为什么停服务再写：**两个文件都以单文件形式挂载进容器；映射文件只在启动时读取，会话文件每个请求都会重新读取。停服务后写入，就能用“临时文件 + 改名”原子替换，网关系统不会读到写了一半的文件，目录服务运行时也不必写网关文件。

**中断与重跑：**第 2 步每建成一个仓库就记录一次，重跑时跳过已有记录的设备；建仓请求带按设备生成的幂等键（[I5](interfaces.md#i5-仓库服务建仓)）。第 3–5 步可以整段重跑。若在“建成仓库”与“写入记录”之间中断，最坏会留下一个空仓库，试运行阶段可以接受。

**已知限制：**每个开通的设备对应一个 Dolt 仓库；网关后端每个请求都会重新读取整个会话文件，开通数量越多，文件越大。开通数量到几千个之前，应先实测（B11）。

`provision --renew-sessions` 只为已开通设备续期会话（同样经过第 3–5 步）。

## 7. 会话与跳转

### 7.1 会话

- 身份 `actor_id = "test1"`（B9），授予网关系统全部 7 项权限（[I4](interfaces.md#i4-写入网关系统的文件)），一个身份就能走通上传、Preview、提交、审核、撤回、历史比较和归档。代码中未发现“不能审核本人提交”的限制。
- 每个已开通设备一条会话，token 为随机值，开通时签发。
- 有效期默认 180 天，可配置；到期前用 `--renew-sessions` 续期。
- 网关系统中的工作区按 `actor_id` 划分，所有人以 `test1` 进入同一设备时共用同一个工作区。试运行只有一个身份，这一点可以接受；多人同时操作同一设备时，需要先线下约定。

### 7.2 跳转

1. 用户在目录中点击“进入提交树”。
2. 目录前端调用 `POST /api/handoffs`，取得跳转地址。
3. 浏览器在当前标签页打开网关前端，地址片段（`#` 之后，不发送给服务器）携带 token、设备键、项目号、显示用的地区路径与项目名，以及返回目录的地址。

### 7.3 网关前端需要补的入口（`frontend/`）

- 启动时若地址片段中有 `gdds-handoff`，解析后设置 `window.__gatewaySession`，随即用 `history.replaceState` 清掉片段。
- 把会话保存在 `sessionStorage`（只在当前标签页内有效，关闭标签页即失效），这样刷新页面后仍在原设备内。这是对现有 `authenticated-fetch` “不在浏览器存储中持久化凭据”约定的试运行例外（Q1，owner 已确认），正式运行接入 SSO 时重新决定。
- 标题栏显示“地区一 / 地区二 / 项目名（站号）”和“返回目录”链接。
- 没有会话时显示“未选择设备，请从设备目录进入”。
- 设备尚无数据（只有初始基线）时，提交树显示“尚无数据”，上传入口照常可用（B7）。网关后端支持在空的初始基线上完成第一次提交，Compose 门禁旅程就是这样走的；工作台在只有初始节点时的显示要在 07 节点上实测，再决定提示放在哪里。

不同标签页可以分别进入不同设备，互不影响。

## 8. 目录前端

布局按草图：左侧两层地区树（带项目数），右侧项目表，顶部是全局搜索与最近访问。

- **数据加载：**一次取回完整目录（[I3](interfaces.md#i3-目录服务-http-接口)），带 ETag。约 1.8 万条、压缩后约 0.5–1 MB；地区树、筛选、搜索都在浏览器内完成。
- **地址状态：**`?r1=&r2=&q=&scope=&page=`，从网关系统返回后恢复原位置，链接也可以转发。
- **搜索：**不区分大小写，匹配项目名子串、站号前缀、拼音首字母前缀与子串、全拼子串（导入方提供全拼时）。范围可选“全部地区”或“仅当前地区”。搜索时，左侧数字变为各地区的匹配数。
- **排序（B8）：**按全拼排序，导入方未提供全拼时按项目名的字符编码排序；名称相同的再按站号排序。
- **同名标记：**全目录中名称相同的项目都带“同名”标记，悬停时显示同名数量；靠站号区分。
- **未开通：**“进入”位置显示“未开通”，悬停说明“该设备尚未在网关系统开通”。
- **最近访问：**保存在 `localStorage`，最多 10 条，只存设备键；目录中已不存在的条目自动丢弃。
- **分页：**每页 50 条；↑↓ 选择，Enter 进入，`/` 聚焦搜索，Esc 清除搜索。
- 视觉沿用网关前端的配色与字号，复制所需 token，不依赖 `frontend/` 的代码。

## 9. 部署与测试（试运行）

**部署（B10，同机）：**

- 目录服务单进程，默认端口 8100，配置项见 [I7](interfaces.md#i7-配置)。
- 网关前端以 `vite preview`（或同类静态服务）运行，`/v1` 代理到 backend 的 8000 端口。
- 目录命令行需要读写两个网关文件的权限和 Docker 访问权限；目录服务不需要。

**测试：**

- 目录：导入校验、唯一键生成、搜索与排序、跳转接口的单元测试，在 06（后端）和 07（前端）节点运行。
- 网关前端入口：单元测试和 mock e2e，在 07 节点运行。
- 端到端：在 05 节点上导入样例名单 → 开通 2 个设备 → 从目录进入 → 上传 → Preview → 提交 → 审核 → 返回目录切换设备。
- 试运行阶段，目录不并入两个权威测试入口（Q2，owner 已确认）。

## 10. 正式运行前再决定

- 设备唯一键改由其他系统导入（B4），目录不再生成。
- 权限与身份：接入独立的权限系统或 SSO，按人签发会话，替换 `test1`。
- 在目录中显示提交、审核状态：需要网关系统提供按设备批量汇总的只读接口。
- 一个项目多台设备：项目表中的行改为可展开的设备子行，跳转仍以设备为单位。
- 规模评估：仓库数量、会话文件大小、开通耗时。
