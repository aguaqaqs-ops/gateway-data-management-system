### S0 总体设计收口

交付 S0 决议、总体设计、本执行计划及总阶段规划更新。无未决系统边界问题；详细 DTO/schema、调度算法和配置默认值的定稿责任见 §3。S0 完成不等于独审通过、产品实现或试运行启动。

### S1a 存储布局与资源配置

内容：定义 repository/durable/canonical/comparison/export/scratch/metadata 的逻辑位置与部署挂载；全量盘点 artifact put/locate/stream/protection/cleanup 消费者；统一 N/M/E/reserve/W/K 与 Compose 限制。先在单 worker 下完成闭环。

详细设计必须决定多 root 定位方式、同对象多用途的唯一物理归属、缺挂载行为、跨 filesystem staging/copy/publish、清理边界及修改挂载的排空操作。按需直接改 ArtifactRef/Contract，不预建兼容层；同步删除替代实现和修订触及的早期文档。

退出：同盘默认与分盘配置均能实际读写/发布/清理；跨盘复制中断不发布残缺结果；权限/缺挂载/磁盘写满有界失败；保护中的 Head、Attempt、Preview/READY 产物不被删；配置与实际容器限制一致。涉及镜像、mount/权限和部署，必须当前候选必要容器门禁。

详细执行已落成：[存储资源设计](p7-s1a-storage-resource-design.md)、[A–G 执行方案](p7-s1a-execution-plan.md)。作用域为一个 environment/group、一组一 worker；S1b 归属接点随本步提供，目录路由/多组/抽取工具留给后续。

### S1b 基础统计与只读查询

内容：设备库分类逻辑/物理占用、共享与未归属统计、提交前后观测、逐执行尝试资源摘要、限期曲线及只读查询/导出。基础采集复用已存在的 metadata/标准计数器，重扫描异步有界。

详细设计必须确定记录位置、查询 DTO/权限/OpenAPI、版本/配置/输入关联、采样与保留预算、计数器重置/缺失语义、跨 root 和共享对象去重、提交测量时点及受干扰窗口的标注。统计存储不得成为 business commit 成功的必要条件；不新增 durable proof/receipt 体系。

退出：正常、缺失、重试、失败、共享引用、清理后、计数重置和可观测范围有正确表达；查询不能越 scope、泄漏路径、触发全盘扫描或无限返回；单 worker 已有真实输入形成可查询摘要。记录采集开销而不提前承诺零开销。必要的前端展示只做既有风格的最小接入，不以新大屏阻塞后端接口。

### S2a 组内多 worker 执行与恢复

内容：重新设计启动租约判定，原子 claim 与 K 约束、健康持有者并存、过期/崩溃接管、未知 effect 恢复、单 repository writer、RS 并发约束及 worker 观测关联。

优先每 worker 一个 executor；K 可由受控 worker 数实现，W>K 时另明确原子且可恢复的槽位方案。详细设计先修订 Operation Lifecycle owning Contract；重点独审核租约/外部 effect，不建设通用调度器或多机协议。

退出：至少两个 worker 的并发、启动、取消/排空、崩溃和租约失效场景通过；同库写入不重入，迟到结果不覆盖新 owner，未知提交先核结果；一次 worker 故障不让其他健康任务被错误接管；内存预算和容器边界实际有效。

### S2b 同机独立处理组

内容：静态设备到组目录、组内设备到 repository 单一权威、每组独立 backend/control DB/RS/roots/worker 池与资源配额；新增/更新归属有版本核对和唯一写入责任。共享目录只管归属，不存业务任务、审核、租约或 effect，不引入网络文件系统或在线自动迁移。

退出：至少两组能独立运行，错误路由/越组写入被拒绝，组内健康租约与组间故障隔离成立；统计按环境/组可区分，同盘物理容量不被重复承诺。工具接口与目录 schema 在本步实施前细化；S2a 原验收仍独立成立。

### S3 调度、准入与背压

内容：交互优先、批量保底与设备公平；上传/持久队列/executor/RS 分层准入；排队、执行和恢复期限；磁盘低水位；暂停、取消、排队原因与前端/外部 DTO。

队列与公平策略在组内执行；整机预算计所有组的 worker/backend/RS 和共享余量。静态分组允许人工调整负载，不增加跨组在线调度器。

详细设计必须给出一个简单可验证的领取策略、保底/aging 和队列容量参数，明确批量暂停的作用点；检查长队列输入保护、原绝对 deadline 和 TTL 的关系。内存或磁盘拒绝不计作成功容量样本；不靠无限线程或重试维持受理。

退出：小型混合负载证明批量非永久饥饿、交互优先生效、同设备正式历史不乱序；队满/磁盘不足/超时/取消的状态和保护释放正确；不存在运行中事务抢占；前端对接按其独立测试入口验证。

### S4a 外部映射与历史回灌接入

内容：复用映射的注册/查询/禁用/导出核对；确定输入关联及结果协议；受控回灌客户端沿现有 HTTP 业务入口自动审核归档；样本分析作为明确独立用途。外部负责文件发现、版本识别和排序，本系统不再实现这些工作。

首版输入由外部逐设备有序投递：前一版本归档或无变化后继续。版本/输入冲突、同键结果回放、清库后映射重新获取、异常停链、后续独立分析、批量暂停和中断续行都必须有明确定义。程序 actor 不接受异常、不代写人工理由、不直接修改 control DB 或 Dolt；不能因旧 Workspace 占用而绕过门禁。

退出：至少两个设备、每设备多个版本覆盖正常自动归档、无变化、重复输入、结果丢失重放、阶段中断、异常后本设备停止/其他设备继续、可分析与不可分析的后续输入、FULL/MODIFIED_ONLY 正确角色。自然数据缺少某种异常时用小型明确向量补足，不声称实样本已覆盖。外部可查询导入结果、异常和资源摘要。

### S4b 设备全状态测试抽取与加载

内容：静止捕获源组一致集合，默认导出所选设备全部现存历史/审核/终态和未完成任务及必要依赖，在独立环境加载完整 backend/RS/文件集合后正常恢复或观察故障。不要求先排空所有 pending，不提供个别历史选择器或副本回合并。另交付排空后生产换组的受控流程/必要接线；不能把测试复制当生产写入责任转交。

退出：单设备代表闭包、共享依赖、未到期租约/unknown effect/PREPARED、源副本隔离、容量与不兼容拒绝均按[分组补充 §9](p7-processing-groups-and-test-extraction-design.md#9-最低验证责任)验证；缺事实不静默重建为成功。导出表清单/工具协议在本步实施前细化，S4a 回灌验收不被替代。

### S5 默认配置与试运行准备验收

内容：绑定最终产品版本、目标单机规格和实际可用真实样本，选择保守配置；检查全部接口/操作说明，完成最终门禁、分组/回灌/测试副本组合和资源边界验证。默认值必须来自 P6 最终证据及本轮观测，不复制测试节点 worker 数。

交付：配置样例与每个参数的含义/约束/生效方式、支持硬件与输入范围、已观测局限、实际资源拒绝/异常清单、只读 OpenAPI、映射及回灌客户端说明、暂停/排空/诊断/统计导出/受控重建 runbook、逐包与容器门禁 provenance、后续校准建议。

退出：总体设计 §14 满足；长期吞吐/p95 不作为本轮待补门禁，实测不达既定功能/资源边界则不能放行。实际部署与持续历史回灌另行安排，S5 不等待数据积累到任意数量。可重建部署不要求生产级长期备份平台，但必须实际验证中断恢复与原始数据重新导入流程。

## 5. 验证矩阵

| 不变量 | 验证 owner 与最低场景 |
| --- | --- |
| 映射和 scope | 注册/query owner：同 scope 重放、冲突、禁用、跨设备读写拒绝、INITIAL 归属、清库重新注册 |
| 发布和清理 | Artifact owner：同盘/跨盘、复制中断/ENOSPC、缺挂载、受保护对象和共享引用；容器验证 mount/权限 |
| 并发业务结果 | 既有 Contract 固定向量＋小型多设备真实流程：串行/并行正式结果和 digest 一致 |
| 任务恢复与提交 | Runtime/RS owner：健康租约并存、过期接管、迟到结果、effect 前失败和 effect 后响应丢失、重复调用 |
| 队列和保护 | 调度 owner：交互/批量竞争、同设备顺序、队满、排队过期、暂停/取消、输入 TTL 保护 |
| 统计口径 | 查询/采集 owner：去重共享、负净变化、混入维护、缺失/计数重置、失败尝试、授权/分页/保留 |
| 回灌语义 | 业务 owner：自动正常归档、无变化、异常停链、其他设备继续、样本无基线副作用、依赖阻塞 |
| 试运行操作 | 最终部署 owner：排空/重启/查询、导出、受控重建和再次回灌；不以销毁环境替代运行时恢复验证 |

每个不变量一个权威测试 owner，其他层只做必要接线验证。纯解析/统计不创建 Dolt fixture；同构场景参数化；时序敏感 serial；不用复制现有全矩阵补足“证据数量”。合成边界向量与真实输入各自标明用途。

## 6. 测试节点与最终门禁

### 工作包针对性验证，阶段最终候选集中构建（Owner 2026-11-10）

此原则立即用于正在实施的 S1a，并作为 S1b、S2a/S2b、S3、S4a/S4b、S5 细化执行计划和提示词的默认规则；不扩展尚未获准阶段的实施授权。S1a A–F 只做受影响逻辑/Contract 和必要数据验证，G 为集中验收点。后续阶段同样以各自最终候选为集中验收点，不以内部工作包、角色更换或复审轮次触发完整构建、全量 runner 或完整真实旅程。

| 时点 | 验证范围 |
| --- | --- |
| 阶段内工作包 | 受影响静态/类型、focused/unit/Contract；必要真实 filesystem/Dolt 和最小数据链；按实际结果独审/交接后继续 |
| 必要容器接线验证点 | 仅对只能在容器证明且影响后续接线的 mount/权限/entrypoint/cgroup/signal 等行为，在相关实现收敛后做最小 Compose 验证；关联工作包可合并，不重复完整业务矩阵 |
| 各阶段最终候选 | 集中构建必要产品镜像，受影响权威包、必要容器与已确认最小真实范围一次验收；S5/发布仍为全部六包及最终 HEAD 容器门禁，前端按独立入口 |

完整容器证据移交最终候选的工作包以 `deferred` 记录具体验证及执行点，不阻塞无依赖的后续实施；不预填通过、不以延期关闭已发现的正确性问题。依赖基础镜像只在其定义的依赖/锁/工具链等输入变化时重建/传输，产品源码修改复用已有基础镜像与缓存。一次集中验收是正常通过目标；失败修复后按实际影响重建复验，遵守现行停止/DC68 规则。构建/缓存故障停止受影响执行及依赖验收，可继续独立逻辑开发。同次 runner 已通过的 Compose 不单独重跑，carried、最终候选绑定和真实范围确认规则继续有效。

### 节点、闭包与最终证据

全部测试、编译、lint、容器和测量遵守根 AGENTS 与 [testing-conventions](../../../testing-conventions.md)：
