## 3. 分类与归档规则

### 3.1 先查消费者，再分类

对候选逐项判为 `KEEP_CURRENT`（现行权威/消费者）、`KEEP_EVIDENCE`（继续引用的证据）、`ARCHIVE`（已关闭过程材料且可恢复）、`DEFER`（并行占用/用途不明）。归档清单可以按集合说明共同理由，但每个实际移除路径必须有一行。

至少核三类引用：

1. 当前导航、实际 P7/S1a 输入、现行 Contract/ADR/Owner 决议和有效 handoff 对候选的依赖；Markdown 相对链接、文件名、路径字符串与 Git 对象引用分别识别。
2. 产品/测试/runner/闭包/容器构建等对文件内容或路径的真实消费。先 `rg`/`git grep`，再读涉及的调用点；不能仅用“文本零命中”证明动态拼接或 glob 无依赖。
3. 归档组内部及保留文档的链接。归档组可以一起离开当前树；保留的活跃导航改为归档索引/恢复指针。若必须改冻结报告原文才能消除新断链，优先保留依赖目标或延期，不篡改报告。

短文件也可能是现行依据，长 review 也可能含尚未被 Contract/决议吸收的最终结论。若发现仅在历史过程记录中的有效规则，先保留并在索引标明原 owner，登记后续定向收口；本次不自行抽取改写成新规则。

### 3.2 Git 原件归档

采用仓库已有 Git 历史归档方式，不另复制一套长文到仍会被全仓检索的 `archive/` 树，不通过全局忽略规则隐藏现行问题。

删除前固定可从最终 main 历史到达的完整来源提交；核该提交确实包含待归档路径的原字节。普通 git 对象是归档载体，清单是恢复入口；**不要求创建新 tag**。已有退出/归档 tag 不动。对未提交、未跟踪或来源不能保证可达的内容一律不归档；不能先删除再寻找来源。

清单使用普通 TSV（`p6-p7-documentation-cleanup-manifest.tsv`）或同等简单可读格式，字段至少包含：

`action, original_path, source_commit, source_blob, sha256, reason, current_owner_or_successor, dependency_disposition`

记录最终实际动作，`DEFER` 的理由与继续负责者不得隐去。历史原件恢复形式是 `git show <source_commit>:<original_path>`；需要落盘时仅输出到本人临时目录，不覆盖活跃仓库原路径。独立验证者对**所有实际归档文件**读取来源字节并核 SHA256/blob，证明恢复成立；不需要安装新依赖或建设归档工具产品。

不改写已审核提交、原始日志和成功/失败结论。原件中的历史相对链接按来源提交解释，不强行迁移到新产品版本。当前活跃入口仍必须可用；归档只留下 tag 名而缺原路径/提交的做法不合格。

撤回错误归档时，从清单记录的对象恢复该文件并作正常新增提交；先核是否已有他人新同名文件，禁止强制覆盖。禁止 reset 主线或重写已引用归档提交。

## 4. 当前入口与检索验收

`current-context-index.md` 建议约 150 行以内，只设少量直接入口，不复制数百条历史记录。给出最近核对时间和状态依据，区分：

- 当前适用 AGENTS/testing conventions/政策与 owning Contract；文件年代不决定权威。
- P6 已退出的固定锚点；P7/S1a 是设计、授权、实施还是验收状态，不预测未来 exit。
- 按当前任务找源码、Contract、阶段计划和交接的顺序；需要历史原因时才沿归档索引追溯。
- 当前授权出处与适用范围；旧“未授权”只描述其阶段/时点，不能覆盖新明确授权，也不能把旧专项授权扩展到当前任务。
- 实际工作区身份核对方法：从当前 `git worktree list` 找 main，不把过时绝对路径写成永久事实。

不依靠永久硬编码 allowlist 隐藏目录。默认建议先搜当前入口指出的 owner/path；需要全量现行文件时仍可普通 `rg`，历史内容用清单/`git show`。不改 `.gitignore`/`.git/info/exclude`/全局 ripgrep 配置，不删除仍有效的长文件以追求输出短。

代表性检索任务在 A 固定，并在同范围、同命令/问题下记录前后结果：

| 问题 | 最低正确结果 |
| --- | --- |
| 当前阶段与下一入口是什么？ | P6 exit/P7 S1a 实际状态及依据，不落入 P5“当前默认入口” |
| 多 root、发布/保护/清理听谁的？ | S1a 设计与 owning Contract；明确目标设计和已生效实现的区别 |
| 当前节点、失败处理与角色配置在哪里？ | 现行 AGENTS/Owner 授权；不把历史节点或重试许可当当前规则 |
| 原退出/旧结论如何追溯？ | 固定提交、原路径、摘要可恢复；未将原失败改成通过 |
| 哪些老文件仍不能删？ | 能指出测试闭包 P2 文档、legacy oracle 等实际保留依赖及理由 |

统计前后文件量/命中数量/输出字节作为辅助，不宣称它们是模型时延、正确率或 token 成本实测。全文搜索仍可能命中有效历史依据；验收重点是当前入口准确、历史可追溯、新断链和误删为零。

## 6. 验证方式与停止条件

本任务默认仅文档静态核查，可在开发主机读 Git 对象、文件文本、Markdown 链接/锚点、摘要和 diff；不导入产品包，不运行产品 runner/pytest、lint/mypy、编译、Compose、benchmark 或真实旅程，不连接/占用测试节点。不把文档检查写成产品测试通过、carried 或容器验证。

| 核查 | 判据 |
| --- | --- |
| 路径与语义 | 相对固定基线的本任务差异只含白名单；产品、规则、S1a/FE 文件未变；merge 中他人变化与本任务变化分开核 |
| 归档完整性 | 每个移除路径有固定可达来源/原路径/blob/SHA256，逐个恢复校验；非 tracked/未知来源未删除 |
| 活跃引用 | 修改入口/导航及受归档影响的保留引用无新增失效；anchor 同样核对；既有无关断链列基线，不借机全仓修复 |
| 实际消费者 | 已识别测试闭包/脚本/现行设计依赖仍完整；动态引用不确定者保留；不执行产品来“试删是否报错” |
| 检索可用性 | §4 五项能够沿短入口找到正确 owner/状态/原件；前后统计使用相同范围和方法 |
| 主线交接 | 最终分支/main 身份与合入提交明确，无禁动覆盖，无重写旧提交/tag，无他人资源操作 |

每轮失败保留原检查输出/候选和原因；普通断链/清单/导航问题由实施者修复，原审复审。发现可能改产品闭包或规则、原件丢失、S1a 正在依赖归档候选、共享文件冲突时，停受影响项，优先保留/延期，使无冲突文档工作继续。只有确需扩大范围或做新的业务/治理决策才向 Owner 集中报告证据、影响、选项和推荐；未回复不得当成允许。

若意外发现必须改代码/测试/依赖才能完成某归档项，把该项转 `DEFER` 并记录后续 owner；本轮不为了删文件触发产品测试，不升级为全面清理。模型、实际 Git 权限或可达性等真正阻塞按事实说明，不反复请求已获授权的正常操作。
