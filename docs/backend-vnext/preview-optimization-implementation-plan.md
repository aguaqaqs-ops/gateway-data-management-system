# Preview 临时性能优化详细实施方案

2026-11-13。Owner 已确认采用 Terra 协调、两名 Sol 实施、脚本执行测试、Luna 按需核证、Astra 最终独审的安排；本次交付为实施文档，尚未启动产品修改、节点测试或部署。总目标与范围见[总计划](preview-optimization-plan.md)，技术候选见[publication 方案](preview-publication-options.md)。本方案为当前有效角色安排，不改变全仓通用流程。

## 1. 本轮交付与技术边界

本轮从正确性修复完成后的新基线开始，先确认实际热点，再按证据验证并减少 bundle publication 中的重复写入和即时读回，形成一个可审查、可撤销的最小候选。普通 t4 MO 与空 INITIAL 的 FULL 分别提供有限对照；结论可以是保留优化、仅保留结构简化、放弃或证据不足，不要求为证明提速不断加测。

- 保留持久 Preview、READY 前最终完整读验、刷新和重新下载、恢复、Submit 绑定、授权及引用保护；现有异步 API、流式 tar、前端 OPFS 不变。
- 保持现有资源配置：worker 2 CPU / 32 GiB、reserve 8 GiB、N1/M24、单 active；backend 1 CPU / 2 GiB、Repository Service 2 CPU / 4 GiB。执行者核对实际配置，漂移时先解决，不能借节点空闲扩核提速。
- 新基线仍支持 publication 优先时，优先 P3：同 store 内获准的未变成员保留原 ref，只写新内容与必要元数据。P2：将逐件即时读回合并到现有 final，只有收益与语义支持时采用。P2 与 P3 不要求都实施。
- 不实施全内存 Preview、取消 final、existing fast path、通用调度池、业务表并行或跨步骤活对象缓存。业务表并行及其他阶段机会继续保留在总计划 R1–R4，不因人员增加自动开工。
- 产品与测试代码留在 `gw08-dual-env` 的隔离短期候选分支；最终仅将获选改动合回临时分支。不合 main、不推送、不更新 08 A/B 服务、不重置其数据。

已有第二轮 MO 中 publication 加即时读回为 28.463 秒，bundle 为 40.535 秒，端到端为 140.207 秒；它们有包含关系，不能相加，也不能把 publication 全部认作可省时间。历史测量用于定位；新方案的提速判断使用本轮合格同条件对照。05 结果不称为 08 实际延迟。

### 1.1 启动前提：先完成正确性修复

本工作的前置任务是[比较正确性与审核结果复用修复](comparison-correctness-repair-implementation-plan.md)。先完成其 A–D 工作包及约定的必要验收，再启动本轮正式基线采集和优化；性能优化不与尚在变动的比较规则、审计闭包或提交保护实现并行修改。修复期间可以准备运行说明、计时/汇总脚本和核对清单，但不以旧语义运行补齐所谓新基线。

进入本工作时，Terra high 子 agent 在 P0 一次性核收以下交接，不要求另设一轮性能专项审批：

1. 正确性修复的完整最终提交 SHA、分支/工作区、设计/Contract 依据及结束总结；必要依据已纳入其交付，不以未跟踪调查稿替代实际完成记录。
2. 受影响后端、前端、容器及约定真实数据验证和独审的结果引用；阻塞 finding 已关闭，无依赖验收尚停在失败状态。无需为交接重复跑已合格且适用的检查。
3. 最终规则/cache identity、审计与 ready closure、提交绑定及终态保护的实际变更；同步后的 golden/断言及已知限制。
4. 可合法复用的普通 t4 v1/v2 输入、脚本、节点缓存和证据位置。节点是否空闲仍在执行时重新核实，不继承旧占用或假定旧测试 DB 可用。

在修复完成、上述前提满足后，Owner 可以直接按本文 P0→P1→选择 P2/P3→P4 实施，无需再补一份基线计划。本次只更新实施文档，不立即启动修复或性能测试。

### 1.2 新基线采集是本工作的一部分

将含完整正确性修复、尚未加入本轮性能优化的 clean 已提交版本记为 `B0`。若修复最终提交之后已有其他代码变化，先核增量及适用验证；不能直接取移动分支 HEAD 或历史 `1ed28d1` 代替。需要最小计时插桩时，从 B0 形成仅增加观测的固定提交 `B1`，记录 B0→B1 的差异，验证不改变业务行为或执行顺序、不引入额外读取；候选采用同口径观测。B1 是受测的诊断版本，不冒称未经插桩的精确延迟。

| 基线交付 | 执行位置与内容 | 后续用途 |
| --- | --- | --- |
| 新 MO 基线 | P1：节点 A，普通 t4 v1、MODIFIED_ONLY、空 INITIAL，一次受理至匹配结果可读；同次记录现有 materialize/assemble/publish 顶层及 bundle 父段、有限 publication 子段/计数 | 判定修复后的主要耗时和剩余冗余，选择 P2/P3 或收口；不额外再跑一份“纯基线” |
| 新 FULL 基线 | 默认 P4：同节点 A，在 B0/B1 上普通 t4 v1/v2、空 INITIAL，一次；与最终 F 的 FULL 尽量相邻执行 | 两 pair 的同语义前后对照。若首次选型确需 FULL，可把该次前移至 P1，仍只占原第4次数槽，P4不重复补跑 |
| 可复核基线记录 | 完整源码/插桩/扩展/规则身份、输入摘要、资源/缓存条件、节点与起止时间、结果正确性摘要、互斥阶段耗时、读写次数/字节及未知项 | 使后续实施者能按相同条件对照；原始日志和失败保存在既定外置目录，不新建证据平台 |

正确性修复会改变工作量：12 类配置表的行比较、结构判等及后台审计、提交绑定结果的保护均须启用，不能为获得旧速度关闭修复。基线阶段由 Terra 根据修复后的受影响断言核对真实结果，优化阶段由实施 B 接续验证，不能拿修复前行数/风险统计或 digest 当作新语义 oracle；真实输入未覆盖的规则仍依赖正确性任务已有小型向量，不扩成性能合成矩阵。

历史 138.567 秒 MO、226.154 秒 FULL 及两轮诊断只作修复前定位参考，不与修复后候选直接计算优化收益。正确性验收若恰有最终 B0 上相同输入、节点、资源、应用状态、计时边界和必要身份的合格样本，可以核实后复用；缺少关键计时/分类就不能假定已有性能基线。复用样本占对应计划项，不另补满额度。

P1 退出必须给出“publication 仍值得优化 / 仅局部有价值 / 热点已变化或证据不足”的结论及依据。已有阶段指标和有限分类够用即停止细分；不能因历史 28.463 秒而强行推进 P3。热点已变化时交付新基线和下一方向建议，跳过不适用候选；R1–R4 仍须另定范围，不在本轮自动扩展。基线采集、必要插桩及汇总属于本工作的原 P0/P1/P4 时间与 **5＋1 次**预算，正确性修复本身的投入另计。

### 1.3 基线阶段：单个 Terra high 子 agent 完成

P0/P1 的交接核对、基线测量和汇总明确交给 **一个 `gpt-6.1-terra`、`reasoning_effort=high` 子 agent**，新上下文提供本计划、正确性修复最终提交和验收记录。外层主会话负责下达范围与接收交付，不重复巡视或另开协调子 agent。此阶段不启动 Sol 实施者、Luna 核证者或 Astra 独审者，也不为基线报告安排独立评审。

Terra 的任务依次为：

1. 核对 §1.1 的修复交接，直接引用已有合格验收/独审记录，不重新审核修复实现；前提不足时列明具体缺项，不冒称修复已通过。
2. 冻结 B0，复用既有测量脚本；只在必要时补局部计时/计数并形成 B1。完成与观测改动相称的必要检查，不为单纯基线重跑完整正确性验收或全量门禁。
3. 核现场及离线依赖，在合格空闲节点取得本人占用，作为唯一运行负责人完成 P1 普通 MO；FULL 默认保留到 P4，首次选型确需时才按原次数槽前移。
4. 自动采集并核对源码/扩展/输入/资源身份、退出码、匹配结果和关键业务摘要；分析父子计时边界、实际操作计数与未知，不关闭新规则或用旧语义预期判成功。
5. 输出基线结论、是否值得进入 P2/P3、原件索引和次数消耗，停止本人私有运行并释放占用，保留后续可复用的合法输入、脚本和证据。

P4 仍需补 FULL 基线时，恢复同一 Terra 子 agent 或将完整交接交给新的 Terra high 子 agent 执行。节点 A 在该基线运行期间由 Terra 独占负责，交接结束后再由实施 A 执行候选；不能两个角色同时控制同节点。已合格采集的 FULL 不再重复。

基线免独审不免测量有效性：固定 clean 提交、同输入与资源、节点计时独占、成功结果及修复后语义核对必须保留。局部计时、计数和报告汇总不升级为独立评审项目；如所谓插桩实际改变执行路径、资源管理、校验或业务行为，则停止把它当纯观测，按实际改动补必要验证/审核，或退回更简单的测量方式。产品错误保留原件并交回修复流程，不在基线任务内悄悄修算法。

后续可直接使用的委派说明：

> 请开启一个 gpt-6.1-terra high 子 agent，按本计划 §1.1–1.3 完成正确性修复交接核对及 P0/P1 性能基线。先查找并核实修复最终提交和验收交接；使用普通 t4、空 INITIAL、N1/M24 及规定资源，优先复用脚本，仅必要时做局部观测。默认一次 MO，FULL 按 §1.2 安排；不启动 Sol/Luna/Astra，不修改业务算法、不部署 08、不推送。保留全部失败与次数，交付基线报告、证据索引、热点建议和节点收尾状态。

该说明用于单独委派基线，交付后结束该子任务；若后续下达的是完整性能优化工作，则 Terra 可在基线完成后继续承担协调，按新证据选择优化并启用 Sol，不因常规交接重复请 Owner 确认。本文更新本身不启动任何 agent 或测量。

优先复用权威 runner、阶段门禁入口及已有测量脚本；只有缺口才补本轮薄脚本，不建设新 CI 平台、通用调度系统或独立监控服务。机器可核对的字段直接生成结果，若已足够则不启用 Luna。临时步骤自动化成本更高时，协调者可调用既有命令完成，并明确该次唯一运行负责人；脚本执行不意味着无人负责。

基线阶段仅一个 Terra 子 agent（外层主会话占槽另计）。优化实施阶段通常为协调者与两名实施者，共三个活跃 agent；Luna 或 Astra 按需错峰启用，最多四个。两节点的测试进程可以同时运行，不需要两个专职测试 agent。当前四槽位已足够，不再以前置增加到六槽位为条件；如果当前主会话并非 Terra，实际开工时将协调职责交给明确指定的 Terra high，不另保留一个常驻重复协调者。上述人数以 Terra 为主协调会话计；若通过子 agent 承担 Terra 协调而外层主会话也占槽，需将该槽一并计入，并在核证/独审时错峰暂停实施者。本文只记录分配，不能据此声称当前会话已切换模型或 agent 已启动。

角色安排遵循 [AGENTS](../../AGENTS.md) 的实施者负责 focused、脚本承担门禁、按需核证和独立审核规则。创建子 agent 时显式选择上述模型与推理档，使用新上下文提供必要交接；不得让实施或测量任务无说明地继承 Astra。

## 3. 工作区、文件归属和节点

协调者按 §1.1–1.2 从已验收的正确性修复版本冻结基点 `B0`，记录修复最终提交到 B0 的增量及验证依据；历史产品基线 `1ed28d1aacf98742d21f758018996453ef8128f4` 仅用于追溯。不能把历史 SHA 或不断移动的分支名直接当新试验基点。若已有他人产品改动，先识别影响与归属；无关未跟踪前端文档保持不动。

实施 A/B 使用各自 linked worktree 和短期分支，均从已记录基点出发。各线运行负责人通过 LAN 同步明确完整提交 SHA，在节点各自的 clean 测试树执行；固定提交期间不得写树、切版本或替换被测镜像。测试日志和临时产物在 worktree 外。需要 linked worktree 的本地 `legacy` 链接按仓库规则准备。

| 文件/边界 | 默认写入 owner | 协作方式 |

节点 A 优先选已有合格输入/缓存的 05，节点 B 选另一空闲合格专用节点；以执行时连接、占用、服务、磁盘、缓存和真实输入核验为准，不提前宣称空闲。各线运行负责人通过既有入口或本轮脚本原子取得本节点 `/home/dev/gdds-node-busy.d`，仅清理自己的运行并释放自己的标记；由既有入口自行持锁的任务不重复加锁。08 A/B 服务不属于本任务资源。

两条工作线可跨节点并行，但同节点整机单飞，计时期间不运行编译、lint 或其他负载。04/06/07 共享宿主，五节点不等于五套独立硬件；尽量让节点 A 的计时不与同宿主重负载重叠。B 可在 A 编译准备期间测试；实际干扰时调整执行时段，不据 cpuset 推断完全独立。同一种输入的基线与候选对照必须在节点 A 同配置完成，不能用另一节点速度代替。

所有测试、编译、lint、构建和浏览器检查只在专用测试节点执行。源码编辑和只读文档核对可在开发机；离线缓存、Rust 扩展身份、镜像身份、TMPDIR、运行日志按 [testing-conventions](testing-conventions.md) 执行。自动阶段门禁由协调者指定一名运行负责人通过既有 `scripts/run-stage-gate.py` 触发，固定 04，不额外建第三组常驻执行者。

## 4. 分包顺序和并行条件

```text
前置：正确性修复 A–D 完成及必要验收
P0：单个 Terra 子 agent 核交接、冻结 B0、核范围与关键约束
P1：同一 Terra 必要插桩 B1 → 脚本一次修复后 MO → 汇总热点
    不启动 Sol / Luna / Astra，不另设基线独审
                 ↓ 选择优化：启用 Sol A/B；或交付基线后收口
P2/P3：A 实施 → 固定提交 → A 线脚本 focused / 候选 MO
       B 按固定接口适配和测试 → B 线脚本正确性验证
       Terra 核进展；实际 A/B 类改动触发独审，finding 回原作者
                 ↓ 整合为同一个候选 F
P4：Terra 补尚未采集的 FULL 基线 → A 同节点候选 FULL；B 核 F 的消费者
    必要门禁与证据齐备 → Astra 集中独审 → 修复/必要复核 → 协调者收口
```

| 包 | 入口和具体动作 | 交接/退出条件 |

## 5. 固定版本交接与失败处理

每次固定提交进入测试时只需要一份完整运行说明：完整 SHA 与父提交、变更目的/文件归属、受影响断言、选定测试入口与参数、输入/资源档、预期差异、是否触发镜像重建及原因。运行入口先核 clean 与实际构建输入，负责人确认脚本未覆盖的前提，再执行；不使用“测最新分支”这样的浮动指令。

基线由 Terra、优化候选由实施 A/B 分别承担所属节点运行与巡视的唯一责任，程序执行后等待既有进程事件，失败/异常/完成主动交接。协调者不重复启动监控；脚本不自动追加性能运行。运行结果包含实际命令、hostname、起止 UTC/HEAD、exit code、原始日志/SHA、缓存与镜像/扩展身份、实际配置及占用释放事实，敏感设置只记摘要。

发现产品错误时保留失败原件，停止本次及依赖验证，把复现与预期交原作者；修复形成新提交后重跑受影响范围。命令或缓存环境问题按仓库现行规则定位修正，不借此改预期或隐去失败。真实 Preview 已开始即消耗一次预算；脚本及实施者不能自行加跑“确认一下”。无依赖的另一工作线可以继续。

B 测试早于最终 F 的结果只覆盖当时版本。整合后按实际 diff 核复用条件，受影响断言在 F 重跑；权威包/容器沿用只接受既有脚本判定。禁止把 A 的性能版本和 B 的正确性版本拼成“同一最终版本通过”。测试发现需要改代码时，由实施者在自己的树改；被测树保持固定直到该次运行结束。

## 7. 时间、证据与收口
